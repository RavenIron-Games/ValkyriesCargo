# Engine sweep: 0.221.12 server vs 0.221.13 server (the 1.0 playtest)

**Run 2026-09-08, a day before 1.0 lands, by `tools/diff-engine.js` over `docs/ENGINE-SURFACE.md`.**
Same axis throughout: dedicated SERVER against dedicated SERVER, decompiled by
`tools/decompile-builds.sh` from `libs-Tools/GAME-SNAPSHOT-pre-1.0-build21981559/` and
`libs-Tools/GAME-SNAPSHOT-playtest-build23105022/` (Steam public-test build 23105022, GameVersion
0.221.13, network 37). **No 1.0 CLIENT build exists yet**, so nothing here is evidence about the client
half; a second run is owed when one appears.

`docs/TODO.md` §2 says any change in this surface is a stop-ship. **There is one, and it stops the mod
dead on 1.0 rather than degrading it.**

## The stop-ship: `GetStableHashCode` gained an optional parameter

    0.221.12   public static int GetStableHashCode(this string str)
    0.221.13   public static int GetStableHashCode(this string str, bool addToNameHash = true)

**The algorithm is byte-for-byte identical** - same 5381 seed, same `((h << 5) + h) ^ c`, same
`+ num2 * 1566083941`. So every ZDO key value and every prefab hash this mod computes is UNCHANGED, and
no saved world or sidecar is invalidated. That is the good half, and it was the first thing checked.

The bad half is that **C# resolves an optional parameter at the CALL SITE, at OUR compile time.** A call
written `name.GetStableHashCode()` compiles to `call GetStableHashCode(string)` - the one-argument
method - and on 1.0 there is no such method. Verified against the real assemblies, not the decompile:
`assembly_utils` carries arity 1 on 0.221.12 and arity 2 on 0.221.13, with no one-argument overload
beside it.

So on 1.0 every one of this mod's 16 call sites throws `MissingMethodException`, and **most of them are
`static readonly` field initialisers**, which turns it into `TypeInitializationException` - a fault that
poisons the type permanently, so every later touch of it rethrows:

| where | sites | what dies |
|---|---|---|
| `Server/Spawner.cs` | 10 | every ZDO key the bird and the merchant are authored with; the type initialiser takes the whole spawner with it |
| `Libs/ServerSync.cs` | 3 | the version gate and the config lock - **and this file is "not ours" and may not be edited in place** |
| `Client/ComfortReporter.cs` | 2 | `VCargo_rested` / `VCargo_comfort`, so nobody is ever eligible |
| `EngineCheck.cs` | 1 | the probe that checks a key's hash |

This is the same failure mode as the `FileSource` bug fixed in PR #55, one order of magnitude larger,
and it is worth stating plainly why neither was caught before: **a name-and-type probe is a veto against
a member disappearing, and both of these are members that CHANGED SHAPE while keeping their name.** The
sweep below is the tool that catches that class, and this is the run that proves it earns its keep.

## Everything else

`Version.m_networkVersion` / `m_playerVersion` / `m_worldVersion` are gone (renamed and retyped:
`c_networkVersion`, and world version is now the enum `Version.World`), so `EngineCheck.CheckVersion`
reports "is gone or is not a number" rather than silently claiming "same build" - correct behaviour,
still wants the rename. `World.GetWorldSavePath` is gone, fixed in PR #55. `RandEventSystem.SaveAsync`
is gone (persistence only; the runtime API the director drives is untouched).

Two rows are reassuring rather than alarming: `ZNetScene.InActiveArea` and `ZoneSystem.GetZone` are
signature-only changes (`Vector2i` -> `Vector2s`) whose BODIES are identical, which is why D5 and
`Core/ZoneOwnership.cs` cross the version step untouched. `ZDOMan.ReleaseNearbyZDOS` does not appear in
any changed list at all.

## The 15 body changes, read (2026-09-08)

Each one was opened in both trees and judged against the engine fact this mod records for it. **One
fact is broken, and it is a second stop-ship.** The rest hold, and they hold for reasons worth writing

### BROKEN - `ZNet.GetAllCharacterZDOS` returns nothing on a dedicated server

    0.221.12                              0.221.13
    List<ZDO> list = new List<ZDO>();     if (m_characterID == ZDOID.None)
    ZDO zDO = GetZDO(m_characterID);          return Array.Empty<ZDO>().ToList();
    if (zDO != null) list.Add(zDO);       List<ZDO> list = new List<ZDO>();
    foreach (peer in m_peers) ...         ... unchanged from here down

On 0.221.12 a dedicated server has no local character, `GetZDO(None)` returns null, that entry is
skipped, **and the loop over `m_peers` still collects every connected player.** On 1.0 the new guard
returns an empty list *before the peer loop runs at all*.

`m_characterID` is set in exactly one place - `ZNet.SetCharacterID`, called only from
`Game.SpawnPlayer`, which spawns the LOCAL player. **A dedicated server never spawns one, so
`m_characterID` is `ZDOID.None` for the life of the process.**

`VisitDirector.Gather` calls this once a second and CLAUDE.md records it as "THE server-side 'where is
every player'". On a 1.0 dedicated server that is now false: the eligibility view is empty forever, so
no player is ever a candidate and **no visit can ever happen.** Nothing throws. The boot line is clean,
`director up` prints, and the roll reports `no eligible player: nobody online` with a full server. It is
the quietest possible failure, which is what makes it worse than the `GetStableHashCode` break above.

A listen host is unaffected: it has a local player, so `m_characterID` is set.

### WATCH - changed meaning, no break today

`ZDO.IsValid` was `(m_dataFlags & DataFlags.Valid) != 0` and is now `m_prefab != -1`; the `Valid` setter
writes `m_prefab = value ? 0 : -1`. Same concept, different storage - this is the `DataFlags.Valid`
(bit 128) removal MigrationStation flagged, with `OutsideZones` taking the bit. Our three call sites
(`Spawner.Tick`, `Spawner.Reclaim`, `CargoFlight.Drop`) all run long after `SetPrefab`, so nothing
breaks. But a ZDO is now INVALID in the window between `CreateNewZDO` and `SetPrefab`, and
`Spawner.Author` closes that window on the next line. It must keep doing so.
