# WindowsDEV — Windows 11 VM with RTX 4070 GPU Passthrough (Linux host)

**Why this exists:** DLNE ([DistributedLLMEngine.md](DistributedLLMEngine.md)) is cross-platform, but its Windows path is not exercisable from a Linux daily driver — `nvidia-smi` on Windows, the PowerShell `Get-CimInstance Win32_VideoController` GPU probe in `engine/hardware.py`, the PyInstaller single-file build, and the code-signing pipeline all need a real Windows box with a real NVIDIA GPU. This is that box, as a VM, with the host's discrete GPU handed to it at the PCI level so the guest sees genuine hardware rather than an emulated adapter.

Built and verified **2026-08-14** on `portoBOX` (ASUS ROG Strix G16, i9-14900HX + RTX 4070 Mobile, Arch Linux, KDE Plasma 6 Wayland). Everything below is measured on that machine, not copied from a guide.

---

## ⛔ READ FIRST — the four things that cost the most time

**1. `supergfxd` ships with Vfio mode hidden.** `/etc/supergfxd.conf` has `"vfio_enable": false` out of the box. Until that is `true`, `supergfxctl -s` does not list `Vfio` and every attempt to select it looks like the feature is unsupported on the hardware. It isn't — it's a config gate.

**2. Never perform the Vfio transition at runtime. Reboot into it instead.** This is the expensive one. `supergfxd`'s runtime transition has a race it loses on this machine:

```
[ERROR supergfxctl::controller] Action thread errored: Modprobe error:
  rmmod nvidia failed: "rmmod: ERROR: Module nvidia is in use by: nvidia_modeset"
```

The sequence is `WriteModprobeConf` → `CheckVulkanIcd` → **`RescanPci`** → `KillNvidia` → `UnloadGpuDrivers`. That PCI rescan lets udev re-load the nvidia stack behind the daemon's back; `UnloadGpuDrivers` then logs *"Driver nvidia_modeset was not loaded, skipping rmmod"* — believing its own stale view — and goes straight for `nvidia`, which `nvidia_modeset` is by then holding.

The damage is not recoverable from userspace. The kernel logs `NVRM: Attempting to remove device 0000:01:00.0 with non-zero usage count!` and the module ends at **refcount `-1`**:

```
$ lsmod | grep nvidia
nvidia   ...  -1
```

**A module at usage count `-1` cannot be removed by any command.** `modprobe -r` on it takes the graphical session down with it, and `supergfxd` wedges in `deactivating` until systemd SIGKILLs it (`State 'stop-sigterm' timed out`). Only a reboot clears it.

**The fix is to skip the transition entirely.** Before it dies, `supergfxd` has *already written* the config that makes the next boot correct — `/etc/modprobe.d/supergfxd.conf`:

```
# Automatically generated by supergfxd
blacklist nouveau
blacklist nvidia_drm
blacklist nvidia_uvm
blacklist nvidia_modeset
blacklist nvidia
options vfio-pci ids=10DE:2860,10DE:22BD,
```

So set the target mode in the daemon's own config and reboot into it. nvidia never loads, vfio-pci claims the card at boot, and there is no teardown to race:

```bash
sudo sed -i 's/"mode": "[A-Za-z]*"/"mode": "Vfio"/' /etc/supergfxd.conf
sudo reboot
```

Clean every time. Do the same to come back (`"mode": "Hybrid"`).

**3. `snd_hda_intel` steals the GPU's audio function on boot, and the VM won't start.** Despite `ids=` naming both devices, only `01:00.0` comes up on vfio-pci:

```
0000:01:00.0 -> vfio-pci        ✓
0000:01:00.1 -> snd_hda_intel   ✗
```

The trailing comma in supergfxd's generated `ids=10DE:2860,10DE:22BD,` is the likely cause. It matters because **both functions share IOMMU group 14** — one non-vfio driver in the group makes the whole group *not viable*, and QEMU refuses with `group 14 is not viable`. Confusingly `/dev/vfio/14` still exists, so the node's presence is not proof of a working setup; check the drivers.

Rebind by hand, **every boot**:

```bash
echo "0000:01:00.1" | sudo tee /sys/bus/pci/drivers/snd_hda_intel/unbind
echo "vfio-pci"     | sudo tee /sys/bus/pci/devices/0000:01:00.1/driver_override
echo "0000:01:00.1" | sudo tee /sys/bus/pci/drivers_probe
```

**4. Arch's edk2 has no `enrolled-keys` firmware descriptor.** Asking for it in the domain XML fails to define with a message that names neither the feature nor the reason:

```
error: operation failed: Unable to find 'efi' firmware that is compatible with the current configuration
```

`/usr/share/qemu/firmware/50-edk2-ovmf-x86_64-secure-4m.json` advertises `['acpi-s3','acpi-s4','amd-sev','requires-smm','secure-boot','verbose-dynamic']` — no `enrolled-keys`, because Arch ships a blank `OVMF_VARS.4m.fd`. Request only `secure-boot`, then populate the varstore yourself after the domain is defined:

```bash
sudo virt-fw-vars --input /var/lib/libvirt/qemu/nvram/win11-gpu_VARS.fd \
                  --output /var/lib/libvirt/qemu/nvram/win11-gpu_VARS.fd \
                  --enroll-redhat --secure-boot
sudo virt-fw-vars --input /var/lib/libvirt/qemu/nvram/win11-gpu_VARS.fd --print
# expect: PK 976 bytes, KEK 4042 bytes, db 7636 bytes, dbx 76 bytes, SecureBootEnable ON
```

Windows 11 checks Secure Boot + TPM at install; without this the installer refuses.

## Host facts (measured, `portoBOX`)

| Fact | Value |
|---|---|
| IOMMU | **On by default** — no `intel_iommu=on` needed. 23 groups. |
| Group 14 | Exactly `0000:01:00.0` [`10de:2860`] + `0000:01:00.1` [`10de:22bd`] — cleanly isolated, **no ACS override patch** |
| vBIOS | Dumpable from `/sys/bus/pci/devices/0000:01:00.0/rom` (524288 bytes) — not needed so far |
| Virt | `vmx` + `kvm_intel` present |
| Outputs | dGPU owns `DP-3`/`HDMI-A-3` — a passed-through guest can drive a **real external monitor** directly, likely avoiding Looking Glass |
| Panel | `card1-eDP-1` on i915 (1920x1200@165) — unaffected by any of this, so the reboots are low-risk |
| Bootloader | GRUB (`/etc/default/grub` + `grub-mkconfig`) |
| CPU layout | 8 P-cores = cpu `0–15` (HT), 16 E-cores = cpu `16–31` |

### supergfxd modes

`supergfxctl -s` → `[Integrated, Hybrid, Vfio, AsusMuxDgpu]`

| Mode | Meaning |
|---|---|
| `Integrated` | dGPU powered off/unbound; iGPU only. Also the **staging mode every transition routes through** |
| `Hybrid` | Optimus — iGPU drives panel, dGPU suspended, wakes for PRIME offload |
| `Vfio` | dGPU bound to `vfio-pci`; invisible to Linux. **The passthrough mode** |
| `AsusMuxDgpu` | Ultimate/MUX — firmware MUX wires the panel to the dGPU |

**Transitions are a graph, not a mesh.** `Hybrid → Vfio` is rejected outright (*"You must change to Integrated before you can change to Vfio"*). `AsusMuxDgpu` is a firmware MUX flip needing a reboot on AC, and in that mode the dGPU is physically wired to the panel — **passthrough is impossible from MUX mode by construction**. `Vfio` and `AsusMuxDgpu` are the two furthest-apart states; budget two reboots to swap. **If you bounce between VM work and gaming, rest in `Hybrid`** — one step from Vfio, and offload still gets the full 4070.

**Vfio mode renames `/usr/share/vulkan/icd.d/nvidia_icd.json` → `nvidia_icd.json_inactive`**, so Linux has *no* NVIDIA GPU at all — no CUDA, no Vulkan, no `nvidia-smi` — until you switch back. Expected, not a fault. Worth knowing before wondering why a host-side DLNE worker reports zero VRAM.

## The VM

Domain `win11-gpu` on `qemu:///system`. Deliberately lean — a DLNE test node, not a daily driver.

| | |
|---|---|
| vCPU | 4, **pinned to E-cores `16–19`**; emulator + iothread on `0-3` |
| RAM | 8 GiB |
| Disk | 80 GB qcow2 (sparse), virtio |
| Firmware | q35 + OVMF Secure Boot, `<smm state='on'/>`, TPM 2.0 (`tpm-crb`, emulator backend) |
| GPU | `01:00.0` + `01:00.1` as a **multifunction pair** at guest `04:00.0`/`04:00.1` on a dedicated `pcie-root-port` |
| CPU model | `host-passthrough`, `migratable='off'`, `<cache mode='passthrough'/>`, `invtsc`, full hyperv enlightenments |

### `managed='no'` is deliberate

```xml
<hostdev mode='subsystem' type='pci' managed='no'>
  <source><address domain='0x0000' bus='0x01' slot='0x00' function='0x0'/></source>
  <address type='pci' domain='0x0000' bus='0x04' slot='0x00' function='0x0' multifunction='on'/>
</hostdev>
```

`managed='yes'` makes libvirt rebind the **host** driver when the VM shuts down — which fights supergfxd for ownership of the card and undoes the mode you booted into. With `managed='no'`, supergfxd stays the single authority on what owns the GPU. The cost is that the devices must already be on `vfio-pci` before the VM starts, which is exactly what gotcha #3 is about.

Keep both functions **multifunction on one root port** at `04:00.x`. Splitting the GPU from its own audio function across separate guest slots is a known source of driver misbehaviour in the guest.

### ISOs must live in `/var/lib/libvirt/images/`

`/home/rohan` is `0700` and qemu runs as `libvirt-qemu`, so anything under the home directory is unreadable to the VM regardless of the file's own permissions. Symptom is a permission-denied on the ISO path that looks like a libvirt bug.

## Runbook

**Into passthrough:**

```bash
sudo sed -i 's/"mode": "[A-Za-z]*"/"mode": "Vfio"/' /etc/supergfxd.conf
sudo reboot
# after boot — fix the audio function (gotcha #3)
echo "0000:01:00.1" | sudo tee /sys/bus/pci/drivers/snd_hda_intel/unbind
echo "vfio-pci"     | sudo tee /sys/bus/pci/devices/0000:01:00.1/driver_override
echo "0000:01:00.1" | sudo tee /sys/bus/pci/drivers_probe
```

**Verify before starting the VM** — all four must hold:

```bash
for f in 0 1; do echo "0000:01:00.$f -> $(basename $(readlink -f /sys/bus/pci/devices/0000:01:00.$f/driver))"; done
ls /dev/vfio/            # expect a node named 14
lsmod | grep -E '^(nvidia|vfio)'   # vfio_pci present, nvidia ABSENT
systemctl is-active supergfxd      # active, not deactivating
```

**Run:**

```bash
virsh --connect qemu:///system start win11-gpu
virt-manager        # console; virt-viewer is not installed. spicy -h 127.0.0.1 -p 5900 also works
```

**Back to Linux gaming / host GPU work:**

```bash
sudo sed -i 's/"mode": "[A-Za-z]*"/"mode": "Hybrid"/' /etc/supergfxd.conf
sudo reboot
```

## Guest-side notes

- **No disk at the Windows drive-selection screen** — the disk is virtio. *Load driver* → the virtio-win CD → `viostor\w11\amd64`.
- **The install boots to a UEFI shell if no console is attached.** The *"Press any key to boot from CD"* prompt times out in ~5 s, so attach the console *before* starting. If missed: `exit` at the shell reaches the boot menu, or `virsh reset win11-gpu`.
- **Error 43 did NOT occur — no spoofing needed.** ✅ Verified 2026-08-14 with GPU-Z in the guest: the XML contains **no** `<kvm><hidden state='on'/></kvm>` and **no** `vendor_id`, and the driver still loads and runs clean. Leave them out; only add them if a future driver regresses.
  - Full identity survives passthrough: `NVIDIA GeForce RTX 4070 Laptop GPU`, AD106 A1, **8192 MB**, Device ID `10DE 2860`, Subvendor **ASUS `1043 1B93`**, BIOS `95.06.31.00.4B` with **UEFI** flagged. The guest reads the **real vBIOS through the passthrough** — no `<rom file=...>` override required, which is the step most laptop-dGPU guides insist on.
  - **Resizable BAR: Enabled** — commonly broken under passthrough; works here.
  - OpenCL, CUDA, DirectCompute, DirectML, Vulkan, Ray Tracing all reported present. DirectX 12 (12_2).
  - Driver was whatever Windows Update chose (`32.0.15.5597` / 555.97, May 2024 branch — old, but irrelevant unless you need a current CUDA runtime).
  - `Bus Interface: PCIe x8 4.0 @ x8 1.1` at idle is **normal link-state downclocking**, not a passthrough defect. Note it is **x8**, not x16 — that is the physical wiring of this dGPU, unchanged by virtualization.
- Install the virtio guest agent from the same CD so `virsh` can see guest state.

## Host-side PRIME (for comparison runs in Hybrid)

`prime-run` comes from the **`nvidia-prime`** package, which is *not* installed by default here. It is only a wrapper for three env vars, so it can be skipped:

```bash
__NV_PRIME_RENDER_OFFLOAD=1 __GLX_VENDOR_LIBRARY_NAME=nvidia __VK_LAYER_NV_optimus=NVIDIA_only <cmd>
```

Anything not prefixed runs on the Intel iGPU, which keeps the dGPU suspended.
