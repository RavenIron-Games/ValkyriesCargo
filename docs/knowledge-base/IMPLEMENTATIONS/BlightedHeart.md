# BlightedHeart Mod — Technical System Report

## Overview

BlightedHeart ("BlightedWorldHeart") is a Valheim BepInEx/Jotunn mod that adds a custom raid-boss encounter: a stationary "World Heart" summoned at a vanilla `OfferingBowl` altar using a biome-specific vanilla item as a sacrifice. The boss has a fully custom (non-vanilla) health/damage/AI pipeline, spawns escalating waves of regular enemies and two mid-fight sub-bosses as its health drops, and on death drops a set of 210 procedurally-generated "Blighted" weapon/armor item variants (biome-appropriate palette-swapped/tinted vanilla gear with bonus elemental stats) that must be upgraded at vanilla crafting stations using trophies plus the same materials as their vanilla base item. A custom on-screen boss-health-bar HUD and a full BepInEx config system (per-biome tunables) round out the mod.

### Custom Item Creation & Recipe System (Jotunn CustomItem / CustomRecipe, vanilla-clone technique)

- **Purpose:** Generates ~210 unique "Blighted" weapon/armor/shield item variants (3 weapon suffixes × 3 base weapons × 8 biomes, plus 4 armor suffixes × ~5 base armor pieces × 8 biomes) without any custom 3D models, textures, or icons — entirely by cloning existing vanilla item prefabs through Jotunn, then mutating their shared item-data stats and re-tinting their materials at runtime. This is the "proper item creation" system: it correctly uses Jotunn's `ItemManager`/`CustomItem`/`CustomRecipe` APIs (rather than raw prefab hacking) and includes real production-grade defensive engineering around Valheim's `ObjectDB`/`Recipe` internals (deferred material resolution, corruption-guarding, mod-compat detection).
- **Key files:** `BlightedItemsManager.cs` (entire file), `ConfigManager.cs` (loot-scale config), `Plugin.cs` (registers `BlightedItemsManager.Setup` on the Jotunn hook)

- **Architecture:**
  - `BlightedHeartPlugin.Awake()` subscribes `BlightedItemsManager.Setup` to Jotunn's `PrefabManager.OnVanillaPrefabsAvailable` event — this fires once vanilla prefabs are loaded into `PrefabManager`/`ZNetScene`, guaranteeing `PrefabManager.Instance.GetPrefab("SwordBronze")` etc. resolve.
  - `BlightedItemsManager.Setup()` calls `CreateBiomeItems(biome, weaponBaseNames[], armorBaseNames[])` once per `Heightmap.Biome`, each mapping to a curated list of vanilla base item prefab names appropriate to that biome's tech tier (e.g. Meadows → `Club`/`SpearFlint`/`Bow`; Mistlands → `SwordMistwalker`/`BowSpineSnap`).
  - Per base item, `CreateWeaponVariant`/`CreateArmorVariant` is called 3-4 times with a different "suffix" (Serpent/Wraith/Blight for weapons; Bastion/Serpent/Wraith/Blight for armor), each carrying its own display name, description snippet, and a `System.Action<ItemDrop.ItemData.SharedData>` stat-mutation delegate.
  - Each variant is built via `new CustomItem(newName, basePrefab)` — Jotunn's clone-based constructor: it duplicates the *entire* vanilla prefab (mesh, icon Sprite, animations, equip visuals, `ItemDrop.ItemData.SharedData` struct) under a new prefab name, so no external art assets or AssetBundles are needed at all. Confirmed via grep: the codebase contains zero `AssetBundle`/`Sprite`/`.png`/`LoadAsset` references — 100% of "custom" items are vanilla-prefab clones.
  - The clone's `ItemDrop.m_itemData.m_shared` struct is mutated in place: name (`"Blighted {origName} {suffixName}"`), description (color-tagged effect blurb prepended), base +5% physical scaling, then the suffix-specific delegate (extra elemental damage, armor %, `HitData.DamageModPair` resistances, durability).
  - `TintItemPrefab` walks `GetComponentsInChildren<Renderer>(true)` (including inactive — equip-visual children are inactive on the prefab) and Lerps each material's `_Color` 80% toward a dark-green tint; separately clones and tints `shared.m_armorMaterial` (the material Valheim applies to the character body mesh for armor) so the original vanilla material asset isn't mutated for every other item sharing it.
  - The item is registered via `Jotunn.Managers.ItemManager.Instance.AddItem(customItem)`.
  - A recipe is built as **upgrade-only**: `Jotunn.Configs.RequirementConfig` entries for 2 biome-appropriate trophies at `Amount=0, AmountPerLevel=2` (i.e., 0 cost to craft at level 1, cost scales on upgrade), station picked by `GetStationName` (tiered `piece_workbench`/`forge`/`blackforge` by base-material substring match), then registered with `ItemManager.Instance.AddRecipe(new CustomRecipe(recipeConfig))`.
  - **Deferred vanilla-material injection:** at creation time `ObjectDB.m_recipes` is empty (still inside `OnVanillaPrefabsAvailable`), so the item's base-material cost (e.g. "3 Bronze" for a bronze sword) cannot be looked up yet. The mapping `blightedName -> basePrefab` is stashed in `_deferredRecipeLookups`. A Harmony postfix on `Player.OnSpawned` calls `BlightedItemsManager.ResolveVanillaRecipeMaterials()`, which runs once `ObjectDB.instance` is populated: for each deferred pair it finds the matching vanilla `Recipe` in `ObjectDB.instance.m_recipes`, copies its `m_resources[]` into the blighted recipe with `m_amount=0` (free at level 1) and `m_amountPerLevel` derived from the vanilla recipe (or `amount/2` fallback), and appends them to the existing trophy-only requirement list. `_recipesResolved` latches only on success so a null `ObjectDB.instance` on first call retries on next spawn instead of permanently skipping injection.
  - **Corruption guard:** `ValidateBlightedRecipes()` runs after resolution and scans every `Blighted*`-prefixed recipe in `ObjectDB.instance.m_recipes` for null `m_itemData`/`m_shared`/`m_name`, since vanilla's `GetAvailableRecipes`/`UpdateRecipeList` iterate that list with no null guards — a single corrupted entry throws mid-`foreach` and empties the *entire* recipe list for *every* item, not just Blighted ones. It also proactively fixes `m_shared.m_dlc == null` (vanilla accesses `.Length` on it unguarded) rather than removing the item, and only removes recipes that are truly unrecoverable.
  - **Compat-aware crafting-list hiding:** because Blighted upgrade recipes are "free at level 1" by design (only trophies cost anything, at level>0), they'd otherwise show as instantly craftable in the vanilla Craft tab. A Harmony postfix on `Player.GetAvailableRecipes` (`HideBlightedCrafting`, `[HarmonyPriority(Priority.Last)]`) strips any `Blighted`-prefixed recipe that is "free at level 1" (`IsRecipeFreeAtLevel1`: all `m_resources[].m_amount == 0`) from the Craft tab only (`InventoryGui.instance.InCraftTab()`), unless `Player.NoCostCheat()` is active (vanilla admin/debug "nocost" flag) or a detected compat mod (`WackyMole.WackysDatabase`) is installed. A second Harmony prefix on `Player.AddKnownItem(ItemDrop.ItemData)` auto-discovers all of a picked-up Blighted item's recipe ingredient materials into `Player.m_knownMaterial`, so the Upgrade tab (which does respect discovered-materials visibility) shows the recipe immediately without requiring the player to separately "learn" bronze/iron/etc.
  - Mod-compat detection: `BlightedHeartPlugin.IsWackyDBInstalled` is set in `Awake()` via `BepInEx.Bootstrap.Chainloader.PluginInfos.ContainsKey("WackyMole.WackysDatabase")` and gates both the deferred-material injection and the crafting-list hiding, since that third-party mod has its own recipe database that would conflict.

- **How to implement (step-by-step recipe):**
  1. Add Jotunn (`JotunnLib` NuGet package) and reference the game's `assembly_valheim.dll` (publicized) plus `UnityEngine.Modules`.
  2. In your plugin's `Awake()`, subscribe a setup method to `Jotunn.Managers.PrefabManager.OnVanillaPrefabsAvailable` — do NOT try to create items directly in `Awake()`; vanilla prefabs aren't loaded yet. Unsubscribe at the top of the handler (`PrefabManager.OnVanillaPrefabsAvailable -= Setup;`) so it only runs once.
  3. For each new item variant: `GameObject prefab = PrefabManager.Instance.GetPrefab("BaseVanillaName");` — guard for null (mod might load before/without the base game content, or a name typo).
  4. `var customItem = new CustomItem(newUniquePrefabName, "BaseVanillaName");` — this is Jotunn's clone-based constructor; it deep-clones the vanilla GameObject (mesh, icon, animations) under the new name automatically.
  5. Get `customItem.ItemDrop.m_itemData.m_shared` and mutate fields directly: `m_name`, `m_description`, `m_damages.*`, `m_armor`, `m_maxDurability`, `m_damageModifiers` (add `new HitData.DamageModPair{ m_type=..., m_modifier=... }` for resistances). Always null-check/initialize `m_dlc` to `string.Empty` if null — a null `m_dlc` on ANY recipe in `ObjectDB.m_recipes` crashes vanilla's unguarded `GetAvailableRecipes` for the whole recipe list.
  6. If re-coloring: iterate `customItem.ItemPrefab.GetComponentsInChildren<Renderer>(true)` (must pass `true` — equip-visual child renderers are inactive on the prefab) and mutate `renderer.materials[i].color` via `Color.Lerp`. For armor, separately clone (`new Material(original)`) and tint `shared.m_armorMaterial` — it's a shared asset reference used by the character body renderer, not per-renderer, and must not be mutated in place or it bleeds into the vanilla item.
  7. Call `Jotunn.Managers.ItemManager.Instance.AddItem(customItem)` to register it — this hooks it into `ObjectDB`, `ZNetScene`, and the crafting UI systems.
  8. Build a recipe with `new Jotunn.Entities.CustomRecipe(new Jotunn.Configs.RecipeConfig { Item = newUniquePrefabName, Amount = 1, CraftingStation = "forge"/"piece_workbench"/etc., Requirements = new[]{ new RequirementConfig{ Item="TrophyX", Amount=0, AmountPerLevel=2 } } })`, then `ItemManager.Instance.AddRecipe(recipe)`.
  9. If a recipe needs vanilla materials that aren't resolvable yet (i.e., you want "same materials as the item you're cloning"), stash the `newName -> baseVanillaName` mapping in a dictionary and defer the lookup — hook a Harmony postfix on `Player.OnSpawned` (fires reliably after `ObjectDB` is fully populated in a loaded world) to look up the vanilla item's own `Recipe` in `ObjectDB.instance.m_recipes` by matching `r.m_item.gameObject.name`, then copy/append its `m_resources` into your recipe's `m_resources` array.
  10. Add a defensive validation pass after resolution that scans your own recipes in `ObjectDB.instance.m_recipes` for null `m_itemData`/`m_shared`/`m_name`/`m_dlc` and either fixes-in-place or `RemoveAll`s them — a single bad recipe silently empties every station's recipe list game-wide because vanilla's iteration has no try/catch.
  11. If any items should not be normally craftable (upgrade-only / loot-only), patch `Player.GetAvailableRecipes` (postfix, filter `available` list) and/or `InventoryGui.UpdateRecipeList` (prefix, filter the `recipes` list) to strip them from the Craft tab specifically (check `InventoryGui.instance.InCraftTab()`), while leaving the Upgrade tab logic (which is level/known-material driven) untouched. Respect `Player.NoCostCheat()` so admin/debug "nocost" mode still reveals everything.

- **Reusable pattern/snippet:**
  ```csharp
  PrefabManager.OnVanillaPrefabsAvailable += () => {
      var baseGo = PrefabManager.Instance.GetPrefab("SwordBronze");
      if (baseGo == null) return;

      var item = new CustomItem("MyModded_SwordBronze_Fire", "SwordBronze");
      var shared = item.ItemDrop.m_itemData.m_shared;
      if (shared.m_dlc == null) shared.m_dlc = string.Empty; // avoid crashing GetAvailableRecipes
      shared.m_name = $"{shared.m_name} of Fire";
      shared.m_damages.m_fire += 20f;

      ItemManager.Instance.AddItem(item);
      ItemManager.Instance.AddRecipe(new CustomRecipe(new RecipeConfig {
          Item = "MyModded_SwordBronze_Fire",
          CraftingStation = "forge",
          Requirements = new[] { new RequirementConfig { Item = "Bronze", Amount = 3 } }
      }));
  };
  ```

### Custom Prefab Creation + Runtime Component Stripping (non-Character custom boss)

- **Purpose:** Creates a wholly custom stationary "boss" GameObject by cloning a vanilla creature/structure prefab and then, at runtime (not prefab/edit time), destroying every vanilla gameplay component (`Character`, `BaseAI`, `Animator`, `Rigidbody`, `Aoe`, `Destructible`, etc.) so the object behaves purely according to custom `MonoBehaviour` logic, while still being network-replicated via vanilla's `ZNetView`. This pattern lets a modder build a boss with entirely bespoke health/damage/AI without fighting Valheim's heavyweight `Character`/`Humanoid`/`BaseAI` class hierarchy.
- **Key files:** `Plugin.cs` (`SetupBlightedHeartPrefab`), `BlightedWorldHeartAI.cs` (`Awake()` cleanup block, `IDestructible` implementation)

- **Architecture:**
  - `Plugin.cs.SetupBlightedHeartPrefab()` (subscribed to `PrefabManager.OnVanillaPrefabsAvailable`) calls `PrefabManager.Instance.CreateClonedPrefab("BlightedWorldHeart", "TheHive")` — clones the vanilla beehive-boss-like prefab "TheHive" as a mesh/visual base, wrapped in `new CustomPrefab(go, fixReference: true)` (Jotunn fixes internal prefab references after cloning).
  - The prefab is scaled to 10%, an explicit `ZNetView` is ensured present (added if missing — required for any networked/persistent object), and `BlightedWorldHeartAI` (a plain `MonoBehaviour`, not derived from `Character`) is added as a component. Comment explicitly notes: *"all component cleanup happens at RUNTIME in Awake() because prefab-time DestroyImmediate doesn't survive Valheim's serialization"* — i.e., stripping components at mod-load/prefab-registration time gets silently undone or breaks Jotunn's prefab pipeline, so cleanup must happen the moment each live instance spawns.
  - `PrefabManager.Instance.AddPrefab(heartPrefab)` registers it into `ZNetScene` so it can be `Instantiate`d/spawned by name and replicated over the network.
  - At runtime, `BlightedWorldHeartAI.Awake()` runs the strip sequence in dependency order: (1) components that reference `Character`/`Humanoid` (`CharacterAnimEvent`, `CharacterDrop`, `BaseAI`, `FootStep`, `VisEquipment`), (2) `Character`/`Humanoid` itself, (3) `ZSyncAnimation`, `Animator`, `Rigidbody`, `Aoe`, `MineRock5`, `HitArea`, `Destructible`, (4) all trigger `Collider`s (contact-damage zones), (5) a final catch-all pass over every remaining `MonoBehaviour` that isn't `ZNetView`/`BlightedWorldHeartAI`/`BlightedDamageForwarder`, all via `DestroyImmediate` (immediate, not `Destroy`, because this must complete synchronously within the same `Awake()` before other systems query components on this object this frame).
  - After stripping, every remaining child `Collider` gets a `BlightedDamageForwarder` component added (a small `IDestructible` shim in `Plugin.cs` that just forwards `Damage(hit)` calls to `m_heart`), so Valheim's native "hit this collider with a weapon" pipeline (which looks for `IDestructible` on the collider's GameObject) still routes damage into the custom AI regardless of which child collider was actually hit. A `BoxCollider` is added to the root if no collider exists at all.
- **How to implement (step-by-step recipe):**
  1. Pick a vanilla prefab visually close to what you want (creature, building, whatever has a good mesh) and clone it: `PrefabManager.Instance.CreateClonedPrefab("YourNewName", "VanillaSourceName")`.
  2. Wrap with `new CustomPrefab(go, fixReference: true)` and call `PrefabManager.Instance.AddPrefab(...)` to register into `ZNetScene`.
  3. Ensure a `ZNetView` component exists (add if missing) — required for any object you want network-synced/persisted.
  4. Add your custom `MonoBehaviour` (implementing `IDestructible` if it should be attackable) to the prefab GameObject. Do NOT try to strip vanilla components here at registration time.
  5. In that `MonoBehaviour`'s `Awake()` (which runs per-instance at spawn time, in both prefab-preview and live contexts), destroy unwanted vanilla components via `DestroyImmediate`, in dependency order: things that reference `Character`/`AI` first, then `Character` itself, then animation/physics, then trigger colliders, then a catch-all `GetComponentsInChildren<MonoBehaviour>(true)` sweep excluding your own types and `ZNetView`.
  6. Add a small forwarder `IDestructible` component to every remaining child `Collider`'s GameObject that just calls back into your main behaviour — this is necessary because Valheim's hit-detection looks up `IDestructible` on the specific collider GameObject that was hit, not the root.
  7. Add a fallback root `Collider` if none survived stripping, so the object remains hittable at all.

### Custom Health / Damage Pipeline with Ownership-Aware RPC and ZDO Sync

- **Purpose:** Because the boss has no vanilla `Character` component (stripped, see above), it needs its own complete health/damage/death system that still correctly participates in Valheim's client-server ownership model (`ZNetView`/`ZDO`) so damage and health stay consistent across all connected clients.
- **Key files:** `BlightedWorldHeartAI.cs` (`Awake`, `Damage`, `RPC_HandleDamage`, `Update`, `OnDeath`)
- **Architecture:**
  - Custom `IDestructible.Damage(HitData hit)` is the entry point Valheim's weapon-hit code calls (via the `BlightedDamageForwarder` shim on child colliders, or directly on the root).
  - `Damage()` first rejects damage unless `hit.GetAttacker()` is a player or a tamed creature (`IsPlayer()`/`IsTamed()`) — this blocks contact damage from other hostile mobs, environmental sources, etc.
  - Ownership check: `if (!m_nview.IsOwner()) { m_nview.InvokeRPC("RPC_BlightedHeartDamage", hit); return; }` — if this client isn't the ZDO owner (typically the host, or whichever peer claimed it), the hit is forwarded via a custom RPC instead of applied locally, avoiding desync from multiple clients each independently decrementing health.
  - The custom RPC is registered in `Awake()`: `m_nview.Register<HitData>("RPC_BlightedHeartDamage", RPC_HandleDamage)`, using a name built from `"RPC_BlightedHeartDamage".GetStableHashCode()` stored in a `static readonly int` — deliberately unique to avoid any collision with vanilla or other mods' RPC names on the same `ZNetView`.
  - Damage math: physical (`blunt+slash+pierce+chop+pickaxe`) is summed separately from magic/elemental (`fire+frost+lightning+poison+spirit+damage`), and magic damage is scaled down by a configurable `MagicDamageMultiplier` (default 0.25) before being added — a deliberate "physical weapons are effective, magic is weak" boss design knob, config-driven.
  - `m_health -= totalDamage;` then immediately `m_nview.GetZDO().Set(ZDO_Health, m_health)` — health is persisted directly into the object's ZDO (a network+save-persisted key/value blob) using an `int`-hashed custom key (`"blighted_health".GetStableHashCode()`), rather than any vanilla `Character.m_health` field.
  - Non-owner clients don't run their own damage logic at all — instead, every `Update()` (when `!m_nview.IsOwner()`), they read `m_health`/`m_maxHealth` back out of the ZDO via `GetFloat(ZDO_Health, ...)`, and separately resolve `m_subBoss1`/`m_subBoss2` object references from ZDOIDs stored in the ZDO (`GetZDOID(ZDO_SubBoss1)` → `ZNetScene.instance.FindInstance(zdoid)` → `GetComponent<Character>()`), so all clients stay visually in sync with the owner's authoritative state without each running the fight logic themselves.
  - Death: once `m_health <= 0`, `m_isDead = true` and `OnDeath()` runs (only reachable on the owner, since only the owner mutates health): drops loot, broadcasts a `Player.MessageAllInRange(...)` center-screen message, and destroys the networked object via `m_nview.Destroy()` (only if still owner).
  - Floating combat text is shown via vanilla's `DamageText.instance.ShowText(...)`, reusing the existing UI feedback system despite the fully custom damage pipeline underneath.
- **How to implement (step-by-step recipe):**
  1. Implement `IDestructible` on your custom `MonoBehaviour`; cache `ZNetView` in `Awake()`.
  2. Register a custom RPC name (hashed via `"YourRpcName".GetStableHashCode()`, stored once as `static readonly int`) with `m_nview.Register<HitData>("YourRpcName", YourHandlerMethod)`.
  3. Define stable ZDO key hashes (also via `GetStableHashCode()` on a unique string) for every piece of state you need synced (health, max health, sub-entity ZDOIDs, etc.).
  4. In your `Damage(HitData hit)` method: reject non-relevant attackers first; then check `m_nview.IsOwner()` — if false, `InvokeRPC` to forward the hit to the real owner and return without mutating local state.
  5. If owner: apply your damage formula, write the result into the ZDO with `m_nview.GetZDO().Set(key, value)`, and use `DamageText.instance.ShowText(...)` for visual feedback for free.
  6. In `Update()`, branch on `m_nview.IsOwner()`: owners run game logic (spawning, thresholds, etc.); non-owners just read back ZDO state into local fields for display/UI purposes, plus resolve any referenced networked sub-objects via `ZNetScene.instance.FindInstance(zdoid)`.
  7. On death, drop loot / announce, then `if (m_nview.IsOwner()) m_nview.Destroy();` to remove the networked object cleanly.
  8. Optionally add a Harmony prefix on `Character.Damage` (or your own damage path) with `[HarmonyPriority]`-free ordering to hard-block damage from disallowed attacker types before it ever reaches your object.

### Wave-Spawning and Escalating Sub-Boss AI Director (Boss Fight Choreography)

- **Purpose:** Implements the actual "boss fight" behavior for the World Heart — since it can't move or attack itself (no `Character`/`BaseAI`), the "AI" is really a fight director: it periodically spawns waves of regular hostile mobs around itself, and spawns two escalating "elite" sub-bosses (borrowed vanilla creatures, scaled up and reconfigured) at configurable health-percentage thresholds, turning a stationary damage sponge into a dynamic raid encounter.
- **Key files:** `BlightedWorldHeartAI.cs` (`HandleWaveSpawning`, `SpawnWave`, `CheckSubBossThresholds`, `SpawnSubBoss`, `GetWaveEnemiesForBiome`, `GetSubBossForBiome`), `Plugin.cs` (`BlightedSubBoss` component)
- **Architecture:**
  - `Update()` (owner-only) calls `CheckSubBossThresholds()` then `HandleWaveSpawning()` every frame.
  - **Wave spawning:** `HandleWaveSpawning` gates on a per-biome `WaveTimerSeconds` config (default 8s) measured via `Time.time - _lastWaveTime`. `SpawnWave()` first prunes `m_spawnedEnemies` of null/dead entries, computes `toSpawn = maxEnemies - currentAliveCount` (per-biome `MaxEnemiesPerWave` config, e.g. 6 in Meadows up to 13 in DeepNorth), then for each slot picks a random prefab name from `GetWaveEnemiesForBiome(biome)` (a hardcoded per-biome array of vanilla enemy prefab names, e.g. Meadows → `Boar`/`Neck`/`Greyling`), resolves it via `ZNetScene.instance.GetPrefab(name)`, computes a spawn position via `Random.insideUnitSphere * 10f` offset from the heart and snapped to terrain height via `ZoneSystem.instance.GetSolidHeight(pos, out height)` (falls back to the heart's own Y if no solid ground found — e.g. over water), instantiates it, strips its `CharacterDrop` components (so wave trash doesn't drop vanilla loot), and immediately alerts it (`BaseAI.Alert()`) and force-targets the nearest player within 50m via `MonsterAI.SetTarget(...)` so mobs don't idle before noticing players. An optional `Player.MessageAllInRange` announcement fires per successful wave (config-toggleable, configurable `MessageHud.MessageType`).
  - **Sub-boss escalation:** `CheckSubBossThresholds` compares `m_health / m_maxHealth` against two configurable thresholds (default 50% and 20%) and one-shot-spawns (`_subBoss1Spawned`/`_subBoss2Spawned` latches) via `SpawnSubBoss(index, hpConfig)`. `GetSubBossForBiome` returns a random pick from a curated per-biome vanilla "mini-boss-worthy" creature list (e.g. Swamp → `Draugr_Elite`/`Wraith`/`Abomination`; Plains → `GoblinBrute`/`GoblinShaman`/`Lox`). The spawned instance is scaled `*1.5`, stripped of `CharacterDrop`/`DropOnDestroy`/`SpawnOnDestroy` components (name-string-matched via reflection-free `comp.GetType().Name` check, since those vanilla types aren't referenced directly), then reconfigured via public `Character` API: `SetLevel(3)`, `SetMaxHealth(hp)`, `SetHealth(hp)` — reusing the base game's own leveled-stat scaling rather than reimplementing it.
  - A `BlightedSubBoss` marker component (`Plugin.cs`) is attached to each sub-boss; its only job is forcing `m_character.m_boss = false` in `Awake()` — vanilla's `EnemyHud` tries to draw its own native boss health bar UI for any `Character` with `m_boss = true`, which crashes/conflicts because these creatures don't have the full boss setup vanilla expects; this flag flip suppresses that native bar so only the mod's own custom HUD (see below) displays health.
  - Sub-boss `ZNetView` uid (`ZDOID`) is written into the parent heart's own ZDO (`ZDO_SubBoss1`/`ZDO_SubBoss2` string keys) so other clients (non-owners) can resolve and track the same sub-boss instance for UI purposes.
  - Separately, `[HarmonyPatch(typeof(Character), nameof(Character.RPC_Damage))]` `BlightedSubBossDamagePatch.Prefix` mitigates (not blocks) magic/elemental damage taken by any `Character` carrying `BlightedSubBoss`, using the same `MagicDamageMultiplier` config as the main heart, so magic-damage mitigation is consistent across the whole encounter even though sub-bosses use vanilla `Character` health internally (unlike the heart itself).
- **How to implement (step-by-step recipe):**
  1. Maintain a `List<GameObject> m_spawnedEnemies` and a `float _lastWaveTime`; each `Update()` (owner-only), if `Time.time - _lastWaveTime > interval`, reset the timer and run a spawn pass.
  2. Prune the tracked list of null/dead entries first, compute remaining capacity, then for each new spawn: pick a prefab name from a per-biome/per-context table, `ZNetScene.instance.GetPrefab(name)`, compute a random offset position, snap to ground via `ZoneSystem.instance.GetSolidHeight`, `Instantiate`.
  3. Strip `CharacterDrop` from spawned trash mobs if you don't want them dropping vanilla loot; call `BaseAI.Alert()` and `MonsterAI.SetTarget(Player.GetClosestPlayer(pos, radius).GetComponent<Character>())` to make them immediately hostile instead of idling.
  4. For scripted "sub-boss" escalation, track a health-percentage threshold and a one-shot boolean latch per threshold; when crossed, spawn a real vanilla `Character`-based creature, then reconfigure it post-spawn via its own public API (`SetLevel`, `SetMaxHealth`, `SetHealth`, `transform.localScale`) rather than trying to fight the `Character` class internals.
  5. If reusing a `Character` with `m_boss = true` for a "mini-boss" that shouldn't get vanilla's native boss-bar HUD, add a tiny marker `MonoBehaviour` that flips `m_boss = false` in `Awake()`.
  6. Track spawned sub-boss `ZNetView`/`ZDOID` in the parent object's own ZDO so remote (non-owner) clients can resolve the same instance for display purposes.

### Boss Summon / Altar Trigger System (OfferingBowl Hijack)

- **Purpose:** Lets players summon the boss by sacrificing a specific vanilla item at a modified vanilla `OfferingBowl` (the "boss altar" object type Valheim already uses for Bonemass, Moder, etc.), reusing vanilla's altar visuals/audio/build-up-effect timing instead of building a custom summon object from scratch.
- **Key files:** `BlightedHeartSpawning.cs` (entire file)
- **Architecture:**
  - `[HarmonyPatch(typeof(OfferingBowl))]` with a prefix on `UseItem(Humanoid user, ItemDrop.ItemData item, ref bool __result)`. Checks `__instance.m_bossPrefab != null` (i.e., this bowl instance is configured as a boss altar at all) then resolves the current biome via `Heightmap.FindBiome(bowl.transform.position)` and looks up that biome's `BiomeConfig` (`AltarSummonItem` name string + `AltarSummonAmount` int, both config-driven per biome — e.g. Meadows requires 1 `HardAntler`, Mistlands requires 1 `QueenDrop`).
  - If the item used matches `config.AltarSummonItem.Value` by prefab name: validates stack size, consumes it via `user.GetInventory().RemoveItem(item, amount)`, shows a center message, and calls `SpawnBlightedHeart(bowl, user)` — then sets `__result = true; return false;` to fully short-circuit vanilla's own `UseItem` logic (which would otherwise try to match against `bowl.m_bossPrefab`'s own configured requirement item).
  - If the item doesn't match, `return true` lets vanilla's normal offering-bowl logic run unmodified (so the bowl still works normally for whatever it originally summons, if anything).
  - `SpawnBlightedHeartCoroutine` (run via `bowl.StartCoroutine`): resolves the `"BlightedWorldHeart"` prefab from `PrefabManager.Instance.GetPrefab`, computes a spawn position above the bowl, special-cases the Swamp biome (many swamp altars are inside an enclosed "giant skull" structure — pushes the spawn point 12 units in the direction away from the bowl toward the summoning player, using horizontal-only vector math, to avoid spawning the boss stuck inside geometry), snaps to terrain via `ZoneSystem.instance.GetSolidHeight`, triggers the vanilla bowl's own `m_spawnBossStartEffects` particle/sound effect for visual continuity, `yield return new WaitForSeconds(bowl.m_spawnBossDelay > 0 ? bowl.m_spawnBossDelay : 8f)` (reuses the vanilla bowl's configured delay if present, matching vanilla boss-summon pacing), then instantiates the boss prefab and calls `ai.Initialize(currentBiome)` to configure biome-specific stats/visuals (see next section).
- **How to implement (step-by-step recipe):**
  1. Harmony-patch `OfferingBowl.UseItem` with a prefix taking `(OfferingBowl __instance, Humanoid user, ItemDrop.ItemData item, ref bool __result)`.
  2. Early-return `true` (let vanilla run) unless `__instance.m_bossPrefab != null` and the item matches your custom trigger condition.
  3. On match: validate/consume the item stack via `user.GetInventory().RemoveItem(item, amount)`, set `__result = true`, `return false` to block vanilla's own summon logic for this call.
  4. Spawn your boss inside a coroutine so you can `yield return new WaitForSeconds(...)` and reuse the bowl's own `m_spawnBossStartEffects`/`m_spawnBossDelay` fields for consistent pacing/feel with vanilla altars.
  5. Snap the spawn position to solid ground via `ZoneSystem.instance.GetSolidHeight(pos, out height)`; add biome- or location-specific position nudges if your altar sites have geometry that could trap a large spawned object.
  6. After `Instantiate`, call an `Initialize(...)` method on your boss's custom component to apply any context-dependent setup (biome, difficulty, etc.) since prefab-time state can't know this.

### Custom Boss HUD (Runtime-Built Unity UGUI Health Bars)

- **Purpose:** Displays a persistent on-screen health bar for the main boss plus up to two dynamically-appearing/disappearing sub-boss bars, built entirely from procedurally-created `UnityEngine.UI` GameObjects at runtime (no `.unity` scene assets, no Unity Editor UI prefabs, no AssetBundle) — useful as a general "how to build custom HUD elements in a code-only Valheim mod" pattern.
- **Key files:** `BlightedUIManager.cs` (entire file), `Plugin.cs` (instantiates `BlightedUIManager` as a `DontDestroyOnLoad` singleton GameObject)
- **Architecture:**
  - `Plugin.cs.SetupBlightedHeartPrefab()` creates a standalone `GameObject("BlightedUIManager")`, calls `DontDestroyOnLoad` on it, and adds `BlightedUIManager` — a singleton (`Instance` static property set in its own `Awake()`), independent of the boss prefab's lifecycle so the UI manager survives boss spawn/despawn/scene changes.
  - `BlightedWorldHeartAI.Awake()` calls `BlightedUIManager.Instance.RegisterHeart(this)`; `OnDestroy()` calls `UnregisterHeart(this)`. `RegisterHeart` lazily calls `CreateUI()` the first time (only once `Hud.instance` — vanilla's own HUD singleton — is available, since the custom UI parents itself under `Hud.instance.m_rootObject.transform`).
  - `CreateUI()` locates Valheim's actual UI font by grabbing it off an existing vanilla `Text` component (`Hud.instance.m_rootObject.GetComponentInChildren<Text>(true).font`) so custom text visually matches the game's UI instead of falling back to a generic font — falls back to `Resources.GetBuiltinResource<Font>("Arial.ttf")` only if that lookup fails.
  - Three health bars (main + 2 subs) are built via a shared `CreateHealthBar(name, parent, anchoredPos, size, out rootRt, out fill, out nameText)` helper, each constructed from four child `GameObject`s: a "Trim" `Image` (gold-colored background expanded 2px beyond bounds for a border effect), a "Bkg" `Image` (solid near-black backing), a "Fill" `Image` whose `RectTransform.pivot = (0, 0.5)` so it scales from the left edge like a proper depleting bar, and a "NameText" `Text` with a `Shadow` component added for readability. All layout is done with anchor min/max/pivot/anchoredPosition math rather than a Canvas layout group.
  - Bar fill is updated purely via `fill.transform.localScale = new Vector3(pct, 1, 1)` (`UpdateFill`) — scaling the RectTransform rather than adjusting `fillAmount`/`Image.type = Filled`, which works because the pivot is pinned to the left edge.
  - `LateUpdate()` (chosen over `Update` so it runs after gameplay logic has updated positions/health for the frame) does the following each frame: refreshes `_heartPosition`/tracked sub-boss references while the heart is alive (so the UI can keep tracking sub-bosses' health even after the heart itself is destroyed, since sub-bosses can outlive the heart in the fight's final phase); computes `heartAlive`/`sb1Alive`/`sb2Alive` booleans; hides the whole UI root if nothing is alive; hides it if the local player is farther than 100m from `_heartPosition` (distance-gated visibility, avoiding a boss bar staying on-screen mod-wide); otherwise lazily creates the UI if needed and shows/updates it.
  - `UpdateBars` implements **dynamic relayout**: depending on which subset of {heart, sub1, sub2} is alive, sub-boss bars are resized/repositioned between "half-width side-by-side under the main bar" and "full-width centered" (when the main heart bar has already disappeared but a sub-boss fight continues) — six explicit layout branches covering all alive/dead permutations, adjusting `sizeDelta`, `anchoredPosition`, and `fontSize` per case.
  - `GetLocalizedBlightedName` prefixes sub-boss names with "Blighted " by running the creature's raw internal name through `Localization.instance.Localize(rawName)` first (so vanilla creature names display correctly localized, e.g. not a raw prefab key) unless it already starts with "Blighted".
- **How to implement (step-by-step recipe):**
  1. Create a persistent singleton `MonoBehaviour` (`DontDestroyOnLoad`) to own your custom UI's lifecycle independent of any specific gameplay object.
  2. Wait until `Hud.instance != null` (vanilla's own HUD manager) before building anything, then parent a root `GameObject` (with `RectTransform`) under `Hud.instance.m_rootObject.transform` using `SetParent(parent, false)` (the `false` is important — keeps local anchoring instead of world position).
  3. Grab an existing vanilla `Text` component's `.font` via `GetComponentInChildren<Text>(true)` to match the game's typography for free, instead of shipping/loading a font asset.
  4. Build each bar from layered `Image` GameObjects (trim border → background → fill), with the fill's `RectTransform.pivot` set to `(0, 0.5)` and updated purely via `transform.localScale.x = percentage` for a simple, allocation-free depleting-bar effect.
  5. Drive all show/hide/update logic from `LateUpdate()`, gated on distance-to-player and "is the tracked entity/entities still alive" checks; keep last-known state (position, sub-entity references) cached so the UI can continue tracking objects that may already be destroyed.
  6. If you have a variable number of simultaneously-displayed sub-elements, write explicit per-combination layout branches (resize/reposition) rather than a generic layout group, if you want tight control over "give full width to X once Y disappears" behavior.

### Biome-Scoped Configuration System (BepInEx ConfigEntry, per-biome sections)

- **Purpose:** Provides a fully server-admin-tunable, per-biome difficulty/reward curve (boss HP, sub-boss thresholds/HP, wave size/timer, loot scale, summon item/amount) using standard BepInEx config binding, with `ConfigurationManagerAttributes.IsAdminOnly = true` so only server admins (in a networked game with a config-sync mod, or Jotunn's own sync) can change balance-relevant values.
- **Key files:** `ConfigManager.cs` (entire file)
- **Architecture:**
  - `BiomeConfig` is a small POCO holding one `BepInEx.Configuration.ConfigEntry<T>` per tunable (`BossHP`, `SubBossThreshold1/2`, `SubBoss1/2HP`, `LootScaleFactor`, `MaxEnemiesPerWave`, `WaveTimerSeconds`, `AltarSummonItem`, `AltarSummonAmount`).
  - `BiomeConfigs` is a `Dictionary<Heightmap.Biome, BiomeConfig>`, populated once via `SetupBiomeConfig(...)` called per biome from `SetupConfig(plugin)` with per-biome numeric defaults hardcoded as call-site arguments (readable at a glance as an escalating difficulty table across all 8 biomes, e.g. `BossHP` 3450 in Meadows scaling to 43125 in DeepNorth).
  - Each `ConfigEntry` uses `plugin.Config.Bind(section, key, default, ConfigDescription)` where `section` is `biome.ToString()` (so the generated `.cfg` file naturally groups settings under `[Meadows]`, `[BlackForest]`, etc.), and `ConfigDescription` supplies both a human-readable description string and an `AcceptableValueRange<T>` (BepInEx's built-in clamping/validation, e.g. `BossHP` clamped to `[100, 100000]`) plus the `ConfigurationManagerAttributes { IsAdminOnly = true }` tag (read by the widely-used `ConfigurationManager`/config-sync ecosystem to restrict editing to admins in multiplayer).
  - `plugin.Config.SaveOnConfigSet = true` is set once globally so any runtime edit (e.g. via an in-game config-manager mod) immediately persists to disk.
  - Non-biome-scoped global settings (`DebugMode`, `EnableWaveAnnouncement`, `WaveAnnouncementLocation` (an enum-typed `ConfigEntry<MessageHud.MessageType>`), `MagicDamageMultiplier`) live under a `"General"` section, bound directly as static fields on `BlightedConfigManager` for global access from anywhere in the mod without threading a config reference through every class.
- **How to implement (step-by-step recipe):**
  1. Define a small config-group POCO class holding one `ConfigEntry<T>` field per tunable value for a repeatable "config chunk" (e.g. per-biome, per-tier, per-difficulty).
  2. Store instances in a `Dictionary<TKey, ConfigGroup>` keyed by whatever your repeating dimension is.
  3. Write one parameterized setup method taking the plugin instance, the key, and all default values as arguments; call it once per key from `SetupConfig`, passing hardcoded defaults inline — this keeps the entire balance table visible as a compact, diffable block of method calls rather than scattered across the file.
  4. Use `key.ToString()` as the BepInEx config section name so the generated `.cfg` file is naturally organized/grouped.
  5. Always pass an `AcceptableValueRange<T>` in the `ConfigDescription` for numeric values to get free clamping and a slider UI in config-manager-style mods.
  6. Tag admin/balance-relevant entries with `new ConfigurationManagerAttributes { IsAdminOnly = true }` so multiplayer clients can't self-buff by editing their local config (assuming a config-sync mod, e.g. Jotunn's own `SynchronizationManager` or ConfigSync-family mods, is present to enforce server authority).
  7. Set `plugin.Config.SaveOnConfigSet = true` once during setup so runtime edits from admin tools persist automatically.

### Defensive Harmony Compatibility & Data-Corruption Guard Patterns

- **Purpose:** A cluster of small, load-bearing defensive patterns that aren't a "feature" per se but are directly responsible for the mod not corrupting or crashing vanilla systems shared with other mods — worth documenting separately since they're broadly reusable engineering practices for any Jotunn mod that injects into `ObjectDB`/`Recipe`/crafting UI.
- **Key files:** `BlightedItemsManager.cs` (`ValidateBlightedRecipes`, `HideBlightedCrafting`, `m_dlc` guards), `Plugin.cs` (`IsWackyDBInstalled` detection), `HANDOFF.md` (documents a real regression caused by getting one of these wrong)
- **Architecture / lessons captured:**
  - **Mod-presence detection:** `BepInEx.Bootstrap.Chainloader.PluginInfos.ContainsKey("Other.Mod.GUID")` checked once in `Awake()`, cached to a static bool, and consulted by multiple systems (`BlightedItemsManager`, crafting-hide logic) to disable/alter behavior when a known-conflicting mod is present, rather than trying to hard-detect and patch around the conflict.
  - **Null-guard every field vanilla iterates over without try/catch:** the concrete bug documented in `HANDOFF.md` — a single `Recipe` with `m_item.m_shared.m_dlc == null` in `ObjectDB.m_recipes` throws inside vanilla's `GetAvailableRecipes`/`UpdateRecipeList` `foreach`, which has no exception handling, silently emptying the *entire* recipe list game-wide (not just the mod's own items) for every player and every station. The fix pattern: proactively default such fields (`shared.m_dlc = string.Empty`) at item-creation time, AND run a post-hoc validation/repair pass (`ValidateBlightedRecipes`) after any bulk mutation of `ObjectDB.m_recipes`, removing only truly-unrecoverable entries and logging what was removed.
  - **Respect existing admin/debug flags instead of reinventing them:** `HideBlightedCrafting` checks `Player.NoCostCheat()` (vanilla's own debug/admin "free crafting" flag) directly, since a HANDOFF-documented regression showed a third-party mod's "no-cost mode" toggle turned out to be a thin wrapper around the same vanilla flag — checking the vanilla source of truth avoids fighting multiple mods' independent reimplementations of the same concept.
  - **Prefer additive Harmony postfixes over replacing method bodies** where possible (e.g. `HideBlightedCrafting` as a postfix on `Player.GetAvailableRecipes` filtering the already-built `available` list, rather than a prefix that tries to fully reimplement recipe availability) — lower risk of Harmony patch-order conflicts with other mods patching the same method (the HANDOFF doc's own "next steps" section explicitly flags checking for `[HarmonyPriority]`/`Before`/`After` ordering against a third-party mod that patches the same target method three separate ways).
  - **Wrap defensive/best-effort Harmony patches in try/catch that logs and swallows** (`HideBlightedCrafting`'s outer `try/catch (Exception ex) { Jotunn.Logger.LogWarning(...) }`) so an unexpected interaction degrades to "this specific filtering doesn't apply" rather than crashing recipe list rendering entirely.
- **How to implement (step-by-step recipe):**
  1. In `Awake()`, build a static `bool` per known-conflicting/known-complementary mod via `BepInEx.Bootstrap.Chainloader.PluginInfos.ContainsKey("Their.Plugin.GUID")`, and thread that flag into any system whose behavior should change in that mod's presence.
  2. Whenever you bulk-create or bulk-mutate `Recipe`/`ItemDrop.ItemData` entries that get inserted into `ObjectDB`, write a follow-up validation pass that defensively checks every field vanilla code is known to access without null-guards (cross-reference by reading vanilla's decompiled source for the method you're interacting with, e.g. `GetAvailableRecipes`) and either repairs or removes offending entries, logging counts.
  3. Before adding a "debug/no-cost/admin override" behavior, check whether the base game or another already-installed mod already exposes an equivalent flag (e.g. `Player.NoCostCheat()`) and key off that directly instead of adding a parallel one.
  4. Prefer Harmony postfixes that filter/adjust an already-computed result list over prefixes/transpilers that reimplement logic, specifically for methods you suspect other popular mods might also patch — lower conflict surface.
  5. Wrap any patch whose failure shouldn't be fatal in try/catch with a logged warning, so a compatibility edge case degrades gracefully instead of breaking an entire UI system for all players.

### Loot Drop Systems (Death-Time Drop + On-Damage Wave Drops)

- **Purpose:** Two related but distinct drop mechanisms: (1) the primary "boss kill reward" drop of Blighted gear on death, scaled by the per-biome `LootScaleFactor` config, and (2) a duplicate/secondary drop path inside the AI class itself, additionally scaled by nearby player count for group-loot fairness. Both exist in the codebase (one via a `Character.OnDeath` Harmony patch, one via the AI's own `OnDeath()` method), which is worth flagging explicitly as it's a real design/possible-redundancy quirk in the source, not misreading.
- **Key files:** `BlightedHeartLoot.cs` (entire file — Harmony-patch-based), `BlightedWorldHeartAI.cs` (`DropLoot`/`SpawnDrop` methods — called from its own internal `OnDeath()`)
- **Architecture:**
  - **`BlightedHeartLoot.cs`:** `[HarmonyPatch(typeof(Character), "OnDeath")]` prefix. Checks `__instance.GetComponent<BlightedWorldHeartAI>() != null && __instance.IsOwner()` — note this specific patch target (`Character.OnDeath`) only fires for objects that still carry a live `Character` component; since the main World Heart has its `Character` component `DestroyImmediate`'d at runtime (see prefab-stripping section), this patch realistically only ever fires for the *sub-bosses* (which retain their vanilla `Character`) if one happened to also carry a `BlightedWorldHeartAI` — in practice this path's real-world trigger conditions depend on exact object composition; treat this file as evidence of an evolving/possibly-legacy drop path rather than the sole authoritative one for the main heart, and cross-check against the AI's own `DropLoot` when reimplementing.
  - Both `DropLoot` implementations pull from the same source data: `BlightedItemsManager.BiomeWeaponDrops[biome]` / `BiomeArmorDrops[biome]` (the `List<string>` of prefab names populated during item creation) — combined into one pool of eligible prefab names, then `numDrops` items are picked with `UnityEngine.Random.Range` and spawned at randomized positions (`insideUnitSphere` offset) via `Instantiate`, resolving the prefab via `ZNetScene.instance.GetPrefab(name)` with an `ObjectDB.instance.GetItemPrefab(name)` fallback in the `BlightedHeartLoot.cs` version.
  - `BlightedWorldHeartAI.DropLoot()` (called from its own internal `OnDeath()`, the actually-reliable path since it runs on the object that really has the custom health pipeline) additionally scales drop count by nearby player count: `dropCount = 3 + (playerCount - 1)`, minimum 3, using `Player.GetPlayersInRange(pos, 100f, list)` — a simple linear "more players in the raid = more loot" scaling, independent of the biome's `LootScaleFactor` (which instead influences item *power*, not drop *count*, in this method) — whereas `BlightedHeartLoot.cs`'s version scales count via `Mathf.CeilToInt(2 * scaleFactor)` instead, confirming these are two independently-written drop-count formulas.
- **How to implement (step-by-step recipe):**
  1. Maintain per-category (weapon/armor/etc.) `List<string>` prefab-name pools per difficulty/biome dimension, populated at the same time you register those custom items (see Custom Item Creation system above) — avoids needing to re-derive "which items belong to this drop table" later via string parsing.
  2. On your boss/enemy's death event (prefer driving this from your own custom `OnDeath()` method if you have one, over a generic `Character.OnDeath` Harmony patch, since a Harmony patch on a vanilla method only fires for objects that still have that vanilla component attached — verify this matches your object's actual final component composition after any runtime stripping), combine the relevant pools, pick N random entries, and `Instantiate` each resolved prefab (`ZNetScene.instance.GetPrefab(name)`, falling back to `ObjectDB.instance.GetItemPrefab(name)`) at a randomized offset position near the death point.
  3. Decide your drop-count scaling formula deliberately (flat, per-player, per-difficulty-scalar) and apply it in exactly one place — the source here has two divergent formulas in two files, which is a maintenance smell worth avoiding in a fresh implementation.
