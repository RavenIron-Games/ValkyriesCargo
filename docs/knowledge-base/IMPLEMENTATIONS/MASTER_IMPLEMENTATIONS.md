# ⛔ READ FIRST — MOVING A VALHEIM OBJECT, AND THE THREE WAYS IT SILENTLY DESTROYS PLAYER PROPERTY

**This is the single most expensive class of bug in this workspace. It cost a full player inventory on the first live dedicated-server deployment of Mists of Avalor (2026-08-01), and every mod here that relocates, spawns, or ground-seats an object is exposed to it.**

*Discovered in `MistsofAvalor` (grave relocation); the engine facts are vanilla and apply everywhere. Full writeup: [MistsofAvalor.md](MistsofAvalor.md).*

## The rule

> **Setting a ZDO's position does not move an object.** It is a suggestion that the owning machine is free to overwrite on its next frame — and if the object has a `Rigidbody`, the owner will overwrite it, continuously, all the way out of the world.

## Why — three engine facts that only bite together

**1. Many "props" are physics bodies.** `Player_tombstone` carries `Rigidbody`, `ZSyncTransform`, `Floating`, `FloatingTerrain`, `Container`. Anything standing on mod-placed geometry falls the instant that geometry streams out. Check the component list in a dump before assuming an object is static — `WubarrksEye_Dumps\<run>\Prefabs_Dump.json` lists components per prefab.

**2. `ZSyncTransform` makes the fall *persistent*.** The owner writes its transform into the ZDO every frame, so the object does not merely fall — it **saves itself falling**. Writing a new ZDO position while the owner's GameObject sits somewhere else means the GameObject wins.

**3. `ZoneSystem.GetGroundHeight` returns its own input on a miss — so "is it underground?" is always false on a headless server.**

```csharp
public float GetGroundHeight(Vector3 p) {
    Vector3 origin = p; origin.y = 6000f;
    if (Physics.Raycast(origin, Vector3.down, out var hit, 10000f, m_terrainRayMask))
        return hit.point.y;
    return p.y;                      // <-- MISS: returns what you passed in
}
```

A dedicated server only has terrain colliders for **loaded** zones. Everywhere else the raycast misses, so vanilla's own guard (`TombStone.PositionCheck`) evaluates `if (y < y - 1f)` — permanently false. Worse, `PositionCheck`'s other clause measures drift with **`Utils.DistanceXZ`**, so a straight vertical drop changes neither X nor Z and never triggers either. **Both vanilla safety nets are structurally blind to a falling object on a dedicated server.**

## How to move an object correctly

```csharp
if (!zdo.IsOwner()) zdo.SetOwner(ZDOMan.GetSessionID());  // unowned writes don't bump data revision
zdo.SetPosition(target);                                  // handles sector move + ZDOSectorInvalidated
zdo.Set(ZDOVars.s_spawnPoint, target);                    // or PositionCheck drags it home

// THE STEP EVERYONE MISSES — move the live instance, or ZSyncTransform undoes you next frame
GameObject go = ZNetScene.instance?.FindInstance(zdo.m_uid);
if (go != null) {
    go.transform.position = target;
    var rb = go.GetComponent<Rigidbody>();
    if (rb != null) { rb.position = target; rb.linearVelocity = Vector3.zero; rb.angularVelocity = Vector3.zero; }
}
```

Then **hold it briefly** (re-assert for ~5s): the previous owner keeps writing until the ownership change reaches it, so a one-shot move loses a race you cannot see.

## Ground height that works headless

```csharp
if (ZoneSystem.instance.GetGroundHeight(p, out float h)) return h;   // accurate; only for loaded zones
return WorldGenerator.instance.GetHeight(p.x, p.z);                  // noise math, no colliders, always answers
```

`WorldGenerator.GetHeight` returns **world-space Y** — the engine assigns it directly (`p.y = WorldGenerator.instance.GetHeight(p.x, p.z)`). **Never** fall back to a height derived from a nearby object (`portal.y + lift`); that is precisely what seated a grave at y=61 over empty air.

## Non-negotiable for anything holding player items

Add a **watchdog sweep**, not a one-shot fix. Read candidates straight from the ZDO table (no instances, no colliders, no loaded zones needed), decide whether each is somewhere a player can reach, and drag the lost ones back — on world load and on a slow repeat. Reference implementation: `MistsofAvalor\Core\AvalorGraveGuard.cs`.

## Related traps already documented

- **A `ZDOID` is a session handle, not an identity — never persist anything against one.** `ZDO.Load` opens with `m_uid.SetID(++ZDOID.m_loadID)`: **every ZDO is renumbered every time the world is read off disk.** The id is perfectly stable while the world stays loaded and meaningless the moment it does not, which makes this fail in the nastiest possible way — the feature works all session, all its data survives on disk, and every key in it is orphaned by the next login. It cost TortalPortal's favourites feature exactly that. Persist against something the world itself preserves: **position** for anything static, or a value you write into the ZDO yourself. (Found 2026-08-03; see [TortalPortal.md](TortalPortal.md).)
- **`DestroyZDO` on an unowned ZDO is a silent no-op** — claim, then destroy. (Same "unowned writes are ignored" root cause.)
- **A client's ZDO table holds everything it has ever received, not just nearby zones** — so a local lookup can succeed with *stale* data and never consult the server. Always prefer the server's answer when there is one; keep the local hit as a fallback only.
- **Jotunn `ConsoleCommand.OnlyServer` gates permission, not location** — the command still executes on the machine it was typed into. Server-side work needs an RPC.
- **`TerrainModifier` is ephemeral; only `TerrainOp` → `TerrainComp` persists** — see [MistsofAvalor.md](MistsofAvalor.md).
- **⛔ `-nographics` makes `Graphics.Blit` + `ReadPixels` return EMPTY textures — silently.** Applies to **every project that bakes an AssetBundle or texture from an editor script**, which is most of them. There is no graphics device, so the blit never happens and `ReadPixels` reads an empty target: **no exception, no warning, exit code 0**, and a texture of the right size, format and name containing *nothing*. It then binds perfectly at runtime and renders as a pale untextured blob, so every symptom points at the MATERIAL and none point at the build. AwayFromHome shipped blank albedo *and* normal maps for all of 1.1.0 and it was reported three times as "the model looks like crap", chased through tint, emission, glow, metallic/gloss and full shader property dumps — while the client log kept truthfully reporting `_MainTex=<albedo>` bound. **The tell is bundle size**: 381 KB headless vs **4,779 KB** with a device, for the same 2048² albedo + 2048² normal + 11k-vert mesh. Detailed textures do not crunch to nothing. Guard it at the top of the build entry point — `if (SystemInfo.graphicsDeviceType == GraphicsDeviceType.Null) Fail(...)` — or bake on the CPU (`TextureImporter.isReadable` + `GetPixels()`). **Two force multipliers:** the identical `Blit`/`ReadPixels` call had *already* been diagnosed as broken headless earlier the same day for *measuring* textures, and nobody grepped the file for its other callers — so if you catch this once, find every caller. And Unity writes to `Unity\AssetBundles\` while the csproj embeds `Assets\`; **that copy is manual**, so a good bake plus a stale copy ships the old broken asset with no change in DLL size. (Found 2026-08-13; full write-up in [../HEADLESS-AND-EMPTY-SERVER-FACTS.md](../HEADLESS-AND-EMPTY-SERVER-FACTS.md).)
- **Terrain ops do not arrive in the order you created them** — `ApplyOperation` routes each by RPC to the zone owner, so on a dedicated server network timing decides which overlapping op wins. `LevelTerrain` *sets* height (last writer wins); `SmoothTerrain2` *lerps* toward it (converges). **Level only where every overlapping op wants the same height; anywhere the target varies, smooth.** Identical machinery produced a clean clearing and a stepped road for exactly this reason — see System 30 in [MistsofAvalor.md](MistsofAvalor.md).

## Fatty — food/stomach overhaul mod
*Full detail: [Fatty.md](Fatty.md)*

Overhauls Valheim's eating system: 5-slot stomach (4 food + 1 drink), stacking with diminishing returns, dietary synergy buffs, and a custom non-flashing HUD.

## Shadows of Midgard — stealth-detection AI mod
*Full detail: [ShadowsOfMidgard.md](ShadowsOfMidgard.md)*

Replaces vanilla monster perception with a full stealth-detection simulation (visibility/noise/hiding/camo scoring feeding a 4-tier alertness state machine) that overrides vanilla `BaseAI` sensing via Harmony.

**Rewritten 2026-08-04 (the rewrite was labelled "2.1.0" while in progress; it shipped as the 2.0.x line — 2.0.0 was the first public release, `version.txt` is 2.0.6, hexium carries 2.0.5. Read every "2.1.0" in the detail file as "2.0.x").** The stealth model was ported formula for formula; the engine under it is new. Several entries below are marked ⚠️ because the 1.x technique they describe was **found to be defective and replaced** — those are the highest-value lessons in this file, because each shipped for the whole 1.x line without being noticed.

- **StealthBrain Decision Engine** ⭐ — 10-phase per-AI evaluator pipeline; detection-level integrator + hysteresis state machine. **2.0.x:** evaluation is now per *(creature, player)* pair rather than per creature — a creature can be hunting one player and unaware of another in the same frame. The flee roll is now rate-corrected (`1 - Pow(1-p, dt)`), because re-rolling a per-evaluation probability makes flee chance depend on which scheduler tier the creature happens to be in.
- **Sensing Sub-Systems (Visibility/Noise/Hiding/Camo)** — four independent named-sub-term scoring functions; multiplicative-cover-vs-additive-lighting composition rule. **2.0.x:** computed **once per player per frame**, not once per (creature, player) — none of the four functions takes an observer, so 1.x was doing N times the work for one distinct answer.
- **Time-budgeted cursor scheduler (`Scheduler` + `Budget`)** ⭐ — replaces 1.x's `StealthOvermind` + `CoroutineManager`. Distance tiers by nearest **tracked player** (never `Player.m_localPlayer`), wall-clock dt per pair, hard per-frame ms budget, zero steady-state allocation. **The budget deliberately does not fall through to vanilla when exhausted** — vanilla performs the identical raycast at 20 Hz uncapped in the same frame, so falling through costs *more* than the work you declined. It decays toward false instead.
- ⚠️ **Harmony patch doctrine — the 1.x pattern is RETRACTED.** 1.x used `int.MaxValue` prefix + `int.MinValue` postfix twins to force its answer. See cross-cutting pattern 5 for the full retraction. 2.0.x: prefix only, `Priority.Low`, honour `__runOriginal`, "no opinion" ⇒ run the original. Nine explicit patch targets with argument-type arrays, installed through per-class `CreateClassProcessor`, **never `PatchAll`**.
- ⚠️ **Atomic patch groups** — a genuinely new technique. `BaseAI.CanSenseTarget` reaches the **static** sense helpers, not the instance ones, so patching two of the three leaves target *acquisition* on one perception model and target *retention* on another, in the same frame, for the same creature. The three sense patches install as a unit or roll back together.
- ⚠️ **Never fake `IsAlerted()`.** 1.x patched `BaseAI.IsAlerted` to return its own state. That one patch silently broke alert replication, the animator bool, aggro roars, boss counting, the give-up/leash timer, taming, Sneak XP, cross-client `EnemyHud` agreement — and the **backstab bonus**, which vanilla gates on the target *not* being alerted (decompile L8740), so backstabs paid full multiplier when they should not have. Drive the real `Alert()` / `SetAlerted()` instead; `Alert()` forwards to the owner by RPC, so the call site does not need ownership.
- ⚠️ **The correct damage hook is `Character.m_onDamaged`.** 1.x patched `Character.Damage(HitData)` (runs on the *attacker's* machine when the RPC is *sent*, before validation) and `Character.OnDamaged(HitData)` (which `Humanoid` overrides **without calling base**, so it never fired for greydwarves, draugr, fulings, skeletons, dvergr or trolls — most of the game). Subscribe from a `BaseAI.Awake` postfix, exactly as vanilla itself does at L4032.
- **Capability probe + declared degradation (`VanillaBind`)** ⭐ — a startup table of every vanilla member the mod touches, each row carrying its impact and the consequence of losing it, with *gates* (not rows) deciding whether the patch layer installs. Compiles against the publicized assembly so calls stay direct; the probe only decides install-or-not. This is the pattern for surviving a Valheim 1.0 that renames something.
- **`long` player identity** ⭐ — `Player.GetPlayerID()`, never `ZDOID`. A ZDOID changes on respawn, so keying creature memory to it orphans every creature's memory of you every time you die.
- **StealthExemption (cross-mod opt-out hook)** ⭐ — a clean, minimal ZDO-flag interop contract with zero assembly coupling (type-name-as-API-surface, reflection-probed by the consumer). Frozen surface. Now backed by `SoMInterop`, a full reflection-free read/write API with a `SoM_Ack` contract acknowledgement.
- **Replicated per-creature digest** — one `byte[]` ZDO field encoding every track, gated on real change, so a creature's detection survives an ownership handover. One field, not N scalars: `ZDO.Serialize` resends the whole field set on any revision bump.
- ⚠️ **BehaviorSystem (decision → vanilla-AI bridge)** — movement-authority handoff rules (when to defer to vanilla's pathfinder vs. drive directly). **All the reflection is gone.** 1.x's `FieldRefAccess<BaseAI, Character>("m_targetCreature")` named the wrong declaring type (the field is on `MonsterAI`), threw into a swallowing `catch` in a static constructor, and left ally-calling **silently inert for the entire 1.x line**. Reflection did not make the binding safer — it converted a build error into a silent runtime no-op.
- ⚠️ **Stealth HUD** — draggable screen-space indicators, embedded-resource sprites. **2.0.x parents under `Hud.instance.m_rootObject`** and creates no canvas, scaler, raycaster or `EventSystem` of its own. 1.x created an `EventSystem` in the chainloader behind an "only if none exists" guard that *always* passed there (the game had not built its UI yet), which is the classic swallowed-clicks bug. Parenting under the vanilla HUD also inherits its hide/show and its teardown for free. Disk read/write removed; every UI write is change-gated against the last value actually written.
- **Armor / Item Stealth-Property Classifier** — heuristic keyword-based classification that works against any mod's armor with zero registration, now persisted to a versioned JSON store with hand-edits protected across rebuilds (`UnityEngine.JsonUtility`, **not** Newtonsoft — it is absent from Valheim's Managed folder).
- **Configuration System (SOMConfig)** — the "POCO snapshot mirrored from synced ConfigEntry via SettingChanged" pattern for cheap hot-path config reads, plus TOML schema migration. ⚠️ **`AddLockingConfigEntry` must be registered before any synced entry** — its absence in 1.x left the admin gate permanently dead and let *any* client broadcast its own values server-wide.
- **Debug Logging Framework (StealthDebugger)** ⭐ — per-(object,message-type) throttle-with-always-log-on-transition pattern, solving the "AI logs every frame forever" failure mode.

## The Windows 11 GPU-Passthrough VM (Linux host)
*Full detail: [WindowsDEV-GPU-Passthrough-VM.md](WindowsDEV-GPU-Passthrough-VM.md)*

How the Arch daily driver (`portoBOX`, i9-14900HX + RTX 4070) hands its discrete GPU to a Windows 11 guest at the PCI level, so DLNE and CapAll can be tested against genuine hardware instead of an emulated adapter. Built and verified 2026-08-14. The four findings that cost real time:

- **`supergfxd` hides Vfio mode behind `"vfio_enable": false`** in `/etc/supergfxd.conf`. Until flipped, the mode simply isn't listed and the feature looks unsupported.
- ⛔ **Never do the Vfio transition at runtime — set the mode in the config and reboot into it.** supergfxd's `RescanPci` step lets udev reload the nvidia stack mid-teardown, after which it rmmods `nvidia` while `nvidia_modeset` still holds it. The module ends at **refcount `-1`**, which *no userspace command can undo*; `modprobe -r` on it takes the graphical session down and the daemon wedges in `deactivating` until SIGKILL. Rebooting is not the fallback here, it's the method — supergfxd pre-writes the correct `/etc/modprobe.d/supergfxd.conf`, so the next boot comes up right with no teardown to race.
- **`snd_hda_intel` steals the GPU's audio function `01:00.1` on every boot.** Both functions share IOMMU group 14, so one non-vfio driver makes the group *not viable* and QEMU refuses to start. `/dev/vfio/14` still exists either way — **its presence is not proof of a working setup**; check the drivers. Needs a manual rebind each boot.
- **Arch's edk2 ships no `enrolled-keys` firmware descriptor**, so requesting it fails to define the domain with a message naming neither the feature nor the reason. Request plain `secure-boot` and populate the varstore afterward with `virt-fw-vars --enroll-redhat --secure-boot`.

Also documented there: why the hostdevs are `managed='no'` (`yes` makes libvirt fight supergfxd for the card at VM shutdown), the mode-transition graph (`Hybrid → Vfio` is rejected; route via `Integrated`; `AsusMuxDgpu` can't do passthrough at all), why ISOs must sit in `/var/lib/libvirt/images/`, and the fact that Vfio mode renames the Vulkan ICD so the **host** has no NVIDIA GPU until you switch back.

## Cross-project recurring patterns worth knowing regardless of which project you're in

These techniques appear, independently reinvented or deliberately reused, across multiple projects — they're the highest-value patterns to reach for first in any new mod:

1. **ServerSync-style config sync** (`SharedInfrastructure.md`) — the default for any server-authoritative tunable.
2. **`Player.m_customData` / ZDO custom keys as free persistence** (Fatty, DvergrAllies, DeathBeforeDishonor, WingsoftheValkyrie, ShadowsOfMidgard) — the default for any per-character or per-object state that must survive respawn/relog/multiplayer without hand-rolled save patches or RPCs.
3. **Clone-a-vanilla-prefab-then-mutate** via Jotunn `CustomItem`/`CustomPrefab`/`CreateClonedPrefab` (BlightedHeart, DvergrAllies, WingsoftheValkyrie, MistsofAvalor) — the default for adding any new item/creature/object without shipping art assets.
4. **Runtime-procedural VFX/textures with zero shipped shader/texture assets** (Njord's rune trail, WingsoftheValkyrie's rune wings, MistsofAvalor's rune portal, TortalPortal's rune gateway *and* its entire UI chrome — all descend from the same lineage) — `Shader.Find` priority-list + scored-fallback-scan, Bresenham rasterization, additive-blend-state manual configuration. TortalPortal's `TortalUITheme` is the most advanced member: a **coverage + height** two-buffer painter embossed once at bake time against a single global light, which generalises the family from flat line art to shaded metal (see `TortalPortal.md`).
5. ~~**Max-priority-prefix-replace + min-priority-postfix-reassert**~~ — **RETRACTED 2026-08-04. Do not reach for this.** It was catalogued from ShadowsOfMidgard 1.x, and rebuilding that mod for 2.0.x established it is an anti-pattern with three measured costs: the postfix twin re-runs the entire guard chain to re-assert a value the prefix already wrote (~50 % of SoM's whole patch-layer CPU); `int.MaxValue` actively defeats every sibling mod's ordering, including ones that carry an explicit `HarmonyBefore` on you; and the duplicated guard chain drifts — SoM's seven copies had diverged into three different chains, two of them missing the cross-mod exemption check entirely. **Replacement, now shipping in SoM 2.0.x:** prefix only, at `Priority.Low`, honouring `__runOriginal`, with "no opinion" meaning `return true`. Cede the final say. If you genuinely need it back for one misbehaving third mod, put it behind a default-off config toggle rather than in the default path. Full argument: [ShadowsOfMidgard.md](ShadowsOfMidgard.md).
6. **The Harmony "stash→run original→restore+add delta" bracketing technique** for composing safely with unknown other mods' patches on a shared summing method (Fatty's `GetTotalFoodValue`).
7. **Coroutine-batched, `yield return null`-spread expensive work** to avoid freezing the game (TheEye's dump engine, MistsofAvalor's chunk streaming, DvergrAllies' breeding scan jitter). **Caveat added 2026-08-04:** every long-lived SoM coroutine independently grew the same latent bug — a `while (true)` whose body can `continue` past its only `yield`, which hard-locks the game. It reached production once (the ally loop). ShadowsOfMidgard 2.0.x deleted all of its coroutines in favour of one time-budgeted cursor driven from a single `Update`, on the reasoning that a rule you must remember at every future edit is a rule that will eventually be forgotten. Prefer a cursor for anything that runs for the session's lifetime; keep coroutines for genuinely one-shot batched work like TheEye's dump. If you keep one, **yield unconditionally at the bottom of the loop.**
8. **`Chainloader.PluginInfos.ContainsKey(guid)` soft-dependency detection** with zero hard assembly reference (Njord, DvergrAllies, Fatty, BlightedHeart, MistsofAvalor).
9. **Guarded/cached reflection with graceful per-feature degradation** rather than a hard startup crash when a game update renames/removes a member (WingsoftheValkyrie's `ReflectionUtil`, TheEye's `HarmonyPatcher`, SkyNet's `ServerDeepScan`).
10. **Defensive validation passes after any bulk mutation of vanilla shared collections** (`ObjectDB.m_recipes`, etc.) — BlightedHeart's `ValidateBlightedRecipes` is the canonical documented case, with the exact crash class explained.
11. **Verify procedural graphics offline before ever launching the game** (`TortalPortal.md`) — port the generator verbatim into a throwaway `net8.0` console app with stubbed `Mathf`/`Vector2`/`Color`, composite the result, and hand-write a PNG (`DeflateStream` + Adler-32 + CRC-32, no dependencies). Same spirit as `CSharp/DumpHud` in `SharedInfrastructure.md`: answer the question with an offline console app instead of a game round-trip. Applies to every procedural VFX/texture system in pattern 4 above.
12. **Keep cosmetics off the gameplay path** (TortalPortal's portal menu; BlightedHeart's defensive-patch cluster) — a VFX call that throws inside a shared Harmony prefix aborts everything downstream of it. Put visual side effects in their own `try/catch` helper, with a `finally` that always advances whatever state they own.
13. **Validate the instrument before trusting a fourth fix** (AwayFromHome, 2026-08-13) — the highest-value habit to come out of that project's debugging day, and it generalises to every mod here. Four separate bugs in one session all produced **confident, well-formed, wrong output**: `-nographics` handed back blank textures with exit code 0; `put 3 of 3 animals back` was logged by pinning code that had never moved anything (`transform.position` is reverted from a non-kinematic Rigidbody on the next physics step — use `rb.position`); a smelter telemetry line reported `ZDOVars.s_accTime` as progress when it is `UpdateSmelter`'s sub-second remainder and reads 0–1s whether the machine is perfect or dead (the progress field is `s_bakeTimer`); and a bound-texture log line was true while saying nothing about whether the texture had pixels. **When a symptom survives several confident fixes, stop fixing and go audit what you are measuring with.** Two showstoppers fell out within minutes of that telemetry reporting `bakeTimer` and ownership instead of `accTime`. Corollary for anything that both measures and corrects: record the *corrected* value, not the pre-correction one, or every successful fix reports itself as an anomaly.
14. **Anything that keeps the world simulated with no player present inherits two vanilla assumptions that are false for it** (AwayFromHome) — Valheim **never releases ownership of a persistent ZDO when its owner disconnects** (only non-persistent ones are reassigned), so an object a player touched then logged off from is frozen for everyone alive; and a **dedicated server stops its world clock entirely while empty** (`ZNet.UpdateNetTime` returns early on zero players), so everything measured against it — every `Smelter`, kiln, blast furnace, spinning wheel, windmill — cannot advance at all. Vanilla is right not to care, because the zone would be unloaded anyway. The disguise is that `Tameable` counts down on **real frame time**, so taming keeps working perfectly while production sits dead, which reads as a scheduling bug. Reclaim from sessions absent from `ZNet.GetPeers()`; correct each machine's own `s_startTime` rather than patching the global clock. See [../HEADLESS-AND-EMPTY-SERVER-FACTS.md](../HEADLESS-AND-EMPTY-SERVER-FACTS.md).
15. **When you need a vanilla piece to do something, call the entry point its own UI calls — and copy that caller's ORDER, not just its arguments** (AwayFromHome v1.0.0, 2026-08-15). Valheim's pieces all have a "a player just did this to me" path, and driving it from outside costs no patch surface, leaves every other mod's patches on that method running, and inherits vanilla's validation free. The catch is that the order is load-bearing in ways the signature does not advertise: `Smelter.OnAddOre` checks `IsItemAllowed(item.m_dropPrefab.name)` **before** `RemoveItem`, because `RPC_AddOre` re-validates on arrival and **silently drops** what it rejects — so remove-then-ask deletes the player's ore into a `ZLog` line nobody reads. Generalise it: before driving any piece from outside, ask *does the receiving end re-validate, and what happens to my resource if it says no?*, then put every irreversible step after every check. Three more from the same work, all cheap to get wrong: `m_shared.m_name` (what `Inventory.GetItem`/`m_conversion` match) and `m_dropPrefab.name` (what `IsItemAllowed`/`RPC_AddOre` validate) are **different strings** used two lines apart in the same vanilla method, and `Inventory.GetItem(string)` defaults to the former so a prefab name returns null and reads as "empty"; `ZRoutedRpc.InvokeRoutedRPC` dispatches **synchronously and inline** when the target is yourself (`if (targetPeerID == m_id) HandleRoutedRPC(...)`), so requiring ownership of both ends of a transfer turns take-and-give into one atomic step a disconnect cannot tear in half; and `ZRoutedRpc.Register` tops out at **6** type parameters while `ZNetView.Register` stops at **4**, which is worth checking before designing a message rather than after. Full write-up, plus the three silent failures in mounting a vanilla `Container` on a custom piece and why `CircleProjector` cannot be subclassed for non-circular outlines, in [../VANILLA-PIECE-INTEROP-FACTS.md](../VANILLA-PIECE-INTEROP-FACTS.md).
16. **A boundary is not a line when the things it bounds have bodies** (AwayFromHome v1.0.0) — a correction rule of "outside the region" applied to physical objects makes the region's edge an electric fence: the object touches it, gets corrected, drifts back, gets corrected again, forever. AwayFromHome's stray sweep logged `furthest was a Boar at 0.0m` under an accelerated soak — a boar leaning on its own fence, teleported to the middle of the pen once per poll for a whole visit. The cost is not just churn: **each correction was a physics re-seat, which is the exact event penned animals escape through**, so the fix was actively causing the problem it existed to solve. Give any such rule a tolerance sized to the bodies involved (0.5 m here, comfortably inside a boar's footprint) and it also stops burying real escapes under a drip of zero-distance ones. Same family as lesson 13: the instrument that reports `0.0m` is telling you the rule is wrong, not that the correction worked.

17. **A benchmark that scores your own system will not crash when it is wrong — it will hand you a plausible number pointing the wrong way** (BarrkBOT 195-question local-vs-cloud run, 2026-08-19). Six traps, every one of which produced a green run. **A category at exactly 0% is a grader bug, not a capability gap** — one subcategory scored 0/9 against the reference model's 9/9 because the bot rewrites channel names into clickable `<#id>` mentions (a shipped feature, and the *better* answer) while the grader matched the literal name; real incompetence is noisy, a perfect wipeout is categorical. **A suite of only prohibitions cannot tell a good answer from a JSON blob** — ten replies shipped as the raw tool call written out as text and *all ten graded PASS*, because those cases carried only `mustNotSay` rules and a blob says nothing forbidden; across 27 subcategories nothing asserted the reply was readable, so add one global positive assertion ahead of everything else. **Fix the measurement bugs that flatter you or the number is worthless** — of five found, three were costing the *reference* model; fixed symmetrically the gap went 15 → 11, i.e. *wider*, and an audit that never once moves against you has not finished. **"Nothing happened" and "it finished successfully" are usually the same signal** — `!toolCalls.length` means both "answered from memory" and "the tool ran and this is the prose answer", so a corrective round gated on it fired on 15 successful turns against 6 genuine ones and destroyed 10 correct answers (it was 6-for-6 when gated properly on `!anyToolRan`); before acting on an absence, ask what else produces it. **Re-running only your failures is a ratchet** — it can only move the number up, because the passes re-roll too. **A dashboard that computes the result is a second source of truth** — a live tile derived its own head-to-head with a hardcoded assumption and a hardcoded `v5.6.1` four releases stale, and was the only number anyone saw because the bench printed none in that mode. Plus two cheap ones: a setting validated for a floor and not a ceiling took chat down for six hours while the process stayed up and typing (clamp on *read* as well as write — config files get hand-edited), and a top-level block calling a function that closes over a `const` declared below it throws `Cannot access 'X' before initialization` at runtime only on that path — walked into **twice in one file in one session**. Full write-up in [../SELF-MEASUREMENT-FACTS.md](../SELF-MEASUREMENT-FACTS.md).
18. **Put a benchmark's safety interlock at the transport, never at the tools — and never in the harness** (BarrkBOT, 2026-08-17). Guarding per destructive tool needs a new entry every time a tool is added and a forgotten entry is silently unprotected; count **pipes** instead, of which there are far fewer (BarrkBOT: 43 admin tools, **three** pipes — Discord REST, a TCP game-control socket, FTP). Put the guard inside the *client factory*, not the test harness: a harness-applied wrapper only protects callers that remember to apply it, and a conditional version of exactly that let twenty "ban <name>" steps through and **banned two real members with a benchmark**. A safety interlock must not have a condition to get wrong, and must not have a caller to get wrong either. Full write-up in [../SIDE-EFFECT-ISOLATION-FACTS.md](../SIDE-EFFECT-ISOLATION-FACTS.md).
19. **A guard written as a list of what is forbidden fails silently, in the direction of the harm — invert it and list the exemptions instead** (BarrkBOT 5.6.13–5.6.15, 2026-08-19). A truthfulness guard stripped sentences claiming an action the tools had not actually performed, and it decided what counted by matching a verb list. Three categories arrived over three weeks, **each one added only after a false claim had already reached a real person**: moderation verbs first (`banned`, `kicked`), then configuration after *"The in-game day has been adjusted to 4"* shipped with no tool called and the owner found the file untouched, then messaging after *"I've sent the announcement to the wonderland-chat channel as requested"* shipped with nothing sent. Same failure all three times, and the second and third were **one day apart**: the verb was not on the list, so the sentence was not a claim as far as the guard could tell. A deny-list is a list of lies already told, and it is permanently one category short of the next one. **The fix is to make the *shape* the test** — first person or passive, past participle, no negation — **and write down the exemptions**: reporting and perception verbs (`checked`, `found`, `looked`, `tried`), and the domain's own past tense (*"Bonemass has been defeated"* is a fact about the world, not a claim about the bot). Twelve verbs nobody had listed — `restarted`, `installed`, `pinned`, `promoted`, `archived`, `uploaded`, `reset`, `has been made` — became catchable in one edit. **What you are actually buying is the failure *direction*, and that is the whole argument**: a verb missing from a deny-list ships a lie to a user and is found days later by a human reading the output, while a verb missing from an exemption list mangles one honest reply and *says so in the log the same second*, quoted, so the next unknown case names itself. Every list drifts; make it drift loudly. Two conditions keep it safe enough to ship: keep the outer gate narrow so the catch-all is consulted on almost no turns, and require real morphology (`-ed`/`-en` only) so *"has been running"*, *"has been online"* and *"has been down"* are never even tested. Watch for a permissive regex that was harmless under a fixed list and is catastrophic under a catch-all — `\s*` where `\s+` was meant let the bare first-person `i` match the tail of every word beginning with i, so *"**I**nstalled mods are listed below"* would have been struck as a confession. **Two companions from the same day.** *A wrong destination is invisible to every layer, because every layer succeeded* — an announcement ordered "on the wonderland-chat channel" was posted to the staff channel it was typed in; the API call succeeded, the tool result said success, the reply said success, and none of them was lying, so nothing downstream can ever catch it. Anything that picks a **destination** must have that destination decided in code from the request's own words, exactly like a destructive target, and read from the *instruction* rather than from the payload the instruction dictates — the same order named a second real channel inside the announcement text, for readers to click. And: *validate a guard against the real world's data, not the fixture you invented for it.* The first version of that targeting fix passed 27 self-written tests against an invented channel map and would have mis-aimed **every decorated channel in the real guild** — production names them `help-desk🔧`, `rules-📕`, `〔🤖〕staff-bot-chat`, an exact-name lookup misses all of them, so an order naming one would have read as naming *nowhere* and dragged a correct choice away to somewhere else. One read of the live directory caught it; the probe now runs on the real names. Same family as lesson 13 — the instrument was confident, well-formed, and wrong.
20. **Off-game test harnesses that compile the real mod source** (WingsoftheValkyrie `tests/`, 2026-08-22) — a `net8` console project that pulls the mod's own `net48` `.cs` files in via `<Compile Include>` and supplies hand-written stubs for the handful of game types they touch (`Player`, `ZNet`, `ZRoutedRpc`, `ZoneSystem`, BepInEx's `ConfigFile`). Makes the things that fail *silently* — serialization, config migration, the shape of a file some other system reads — verifiable without launching Valheim. Two rules make it worth having: compile the **shipping** source rather than a copy, and commit **fixtures** rather than reading live machine state, or the harness quietly starts passing against something that drifted. Needs `<Compile Remove="tests/**" />` in the plugin csproj, since the SDK globs `**/*.cs`.

22. **When every stage of an asset is proven faithful and it still renders wrong, suspect the material state that is *not* a property** (AwayFromHome 1.0.2 → 1.0.6, 2026-09-01). Cloning a vanilla piece's material for Valheim's own shader carries three things nobody asked for: `_Color` (multiplied into your albedo), `_ValueNoise` (world-space mottle) and the per-slot **texture scale/offset** (`_MainTex_ST`). The first two are shader properties and a property-table dump shows them; the third is read with `GetTextureScale/Offset` and **no walk of `Shader.GetPropertyCount()` will ever list it**. `sign_notext` carries `scale=(0.33, 0.30)`; over a fragmented 1:1 atlas that put cap-blue on the trunk and gill-cream on the caps, and three releases of texture work — a tint, a shadow lift, a tone remap, each measured and each correctly reasoned — were aimed at a symptom while the shipped DXT1 correlated 0.996 with the source and the bundled mesh matched the GLB index-for-index. The tell was in the complaint itself: the *same* patchwork read "too dark" in shade and "too bright" in daylight, which is colours in the wrong **places**, not at the wrong **levels**. Reset ST to identity on every slot when cloning a donor, log the previous values, print `[st]` beside every texture in the dump. Same family as lesson 13: the instrument was complete-looking and had the one wrong number cropped out. Full write-up as §8 of [../VANILLA-PIECE-INTEROP-FACTS.md](../VANILLA-PIECE-INTEROP-FACTS.md).

23. **`IsZoneLoaded` is a readiness test, not a listing test — and a two-tick oscillation looks like a leak** (AwayFromHome 1.0.8 / LetItGrow 0.1.4, 2026-09-05). The Wonderland server was OOM-killed three times in six days, ~1 GB/hour from boot with nobody online. Both anchors had, on 1 Sep, started feeding `ZNetScene.CreateObjects` only zones that `ZoneSystem.IsZoneLoaded` said were loaded, to stop objects being built over no ground. But `IsZoneLoaded` is `m_zones.ContainsKey && !m_loadingObjectsInZones.ContainsKey`, and `DungeonGenerator`/`LocationProxy` flip that second clause the tick they are instantiated (`SetLoadingInZone`) and clear it in `OnDestroy`. So: list the zone → the crypt's generator is instantiated → the zone is "not loaded" → skip it → `RemoveObjects` destroys the whole zone → it is "loaded" again → list it. Every ring with a dungeon in it was rebuilt every other tick for the whole visit: **19,682 `Loading dungeon` against 315 `Spawning dungeon` in one 24-hour session.** The gate wanted "terrain exists" (`m_zones.ContainsKey`), which is what it now tests; vanilla keeps mid-stream zones listed and defers through `IsZoneReadyForType`. Verified live: 60:60 and a flat 8–9.4 GB over six hours. **Three habits from the hunt.** (1) `journalctl --user -u <unit>` prints a memory peak on every stop — a per-session table of peak vs. wall-clock dates the onset of a leak to the day, before any log is opened (here: stable ~10 GB through 27 Aug, climbing after). (2) Count log lines per day with one awk pass over the whole log and look for a step, not a level — `Loading dungeon` went 600/day → 12,600/day on the first full day after the gate shipped, which named the change. (3) When a paired start/finish line exists (`Loading dungeon` / `Spawning dungeon`), their **ratio** is the diagnosis: 62:1 says "destroyed before it finished" in a way no memory number can. And the general rule: any vanilla predicate you gate on has a second clause — read the decompile for what else makes it false before building a feed on it. Full write-up: [ZoneAnchor.md](ZoneAnchor.md), addendum 2026-09-05; the dedicated-server audit of TortalPortal that came out of the same day is in [TortalPortal.md](TortalPortal.md).

24. **A custom CHARACTER from an AssetBundle has five ways to be silently wrong, and a build script can see none of them** (Valkyrie's Cargo, Ingvar, 2026-09-07). Every one produced a bundle that passed every gate a script can check — right size, right asset count, `SkinnedMeshRenderer=True`, 24 of 24 bones, all six clips, exit code 0 — and they mask each other, so they surface one per screen. **(1)** Blender names actions `Armature|<Clip>`, and that name is what the clip is CALLED in the bundle: a by-name loader misses all six and the character stands frozen, *and* the same string defeats the loop table beside it, so a non-looping idle freezes on its last frame after ten seconds and reads as an animation-driver bug. Strip the prefix BEFORE deciding looping, and fail the build on a surviving `|`. **(2)** Stray source geometry ships — here an unparented 2 m `Icosphere` that rendered as a white ellipsoid swallowing the character — and the only tell is an **80-triangle discrepancy in a 31k mesh**, which looks like rounding noise until you subtract it; the build script had reported the first `SkinnedMeshRenderer`, singular. Enumerate every renderer. **(3) `sharedMesh.bounds` on a skinned mesh is bind-pose data and it lies** — `bounds`, `localBounds` and `sharedMesh.bounds` are the same wrong box wearing three hats, because FBX axis conversion goes into the BONES and never touches it. It put a 1.36 m height on Z and yielded a "0.244 m ground offset" that was **half his width**, then lifted him that far into the air with a perfectly self-consistent log line. `ModelImporter.bakeAxisConversion` does not fix it and neither does re-exporting with `axis_up='Y'` (both tried — the FBX header declares Y-up while the geometry does not). Measure `SkinnedMeshRenderer.BakeMesh` instead, and set `updateWhenOffscreen = true` while you are there, because Unity culls by that same bad box. **(4)** An Editor-baked bundle carries Unity's `Standard` and **Valheim does not light it** — a lit head on a flat black body. Swapping only the shader is the trap: `material.shader = x` keeps only properties matching BY NAME, and the rest fall back to defaults that read black under ambient. Copy the WHOLE material off the vanilla prefab you are replacing (`ZNetScene.GetPrefab` → `sharedMaterial` → `new Material(donor)`, here `DvergerBody`/`Custom/Creature`) and put your albedo in it. **(5)** Then it glowed blue head to foot: the Dverger's glow is an emission colour gated by an emission MASK, and clearing the donor's maps (correct — they are on the donor's UVs) without clearing `_EmissionColor`, the `_EMISSION` keyword and the GI flag lights everything the mask held back. **That last one is lesson 22's mirror** — there, cloning a donor carried things nobody asked for; here cloning is mandatory and it carries the glow. Whenever you clone a vanilla material, enumerate what the donor was doing that you are not. Two non-problems recorded so nobody re-litigates them: a **`StandaloneWindows64` bundle loads fine on a Linux client**, and Unity's material import binds a texture **by name**, so renaming the Blender image datablock to match the PNG beside the model fixes an empty `_MainTex` with no runtime code at all. Debug order that actually converges: dump the hierarchy (renderers, tris, materials, shader, `_MainTex`) → check clip names and loop flags → stand it up and judge the SILHOUETTE before the colour → only then touch materials, one change per look. Full write-up in [../SKINNED-CHARACTER-BUNDLE-FACTS.md](../SKINNED-CHARACTER-BUNDLE-FACTS.md).

25. **`Transform.TransformVector` applies SCALE; Valheim's bone chains are not at 1, and both bugs it caused reported themselves as healthy** (Valkyrie's Cargo, 2026-09-09). A merchant carried by a Valkyrie read as an **empty bird** to every witness for a week, while every log line the mod printed said the carry was fine — `awake as carried`, `ours`, `grounded no` at the drop, no exception, patches and probes all green. Two nights were spent fixing real but unrelated things (a 24 s empty departure leg, a 120 m start altitude that put the approach 53° above the horizon) before a per-second diagnostic printing **his position, the pin's position, and the distance between them** settled it in two lines: `off-pin 50 m`, then `50.0000038`, then `49.9999962`, across three visits and every second of each. **A constant is the whole diagnosis** — gravity beating a pin accelerates and the gap grows; a fixed offset does not move. He was owned, pinned, visible and not falling, fifty metres straight down and off the bottom of the screen. `PinToTalon` used `_pin.TransformVector(offset)` with the prefab's own `m_attachOffset` of `(0, 0.30, 0.40)` — half a metre — and **`TransformVector` applies the transform's scale as well as its rotation**, while the Valkyrie's attach point hangs at `valkyrie2/Armature/.../r_foot/Attach` on a chain about 100× off unit. `TransformDirection` is rotation-only and is what an offset already in world metres wants. **The same factor, the same night, in a second place:** hanging another mod's backpack on the character's spine put it **47.9 m above the bone**, because `SkinnedMeshRenderer.BakeMesh` returns `attach_skin` equipment in the *character root's* space (geometry as if on a standing player), not in bone space — and that attach also reported itself perfectly, `18 part(s), 11206 tris`, while invisible. Re-centre a baked prop on its own combined bounds, through each part's full T/R/S, and log the measured centre. **And a correction worth carrying:** the first published diagnosis blamed the source asset — `ingvar.glb` really does carry `Armature` at scale 0.01 — but Unity's FBX import normalises that, and the runtime read `lossyScale 1`. *Reading the source asset is not reading the runtime.* Print `lossyScale` from the running game before theorising about the exporter. **The transferable habit is the diagnostic, not the fix**: when a thing is in the right state and looks wrong, stop guessing and print the numbers that are *different* for each competing explanation — position vs. anchor, the gap, the renderer count, the owner — in one line, once a second. Three candidate causes died on the first flight it ran. Same family as lessons 13 and 22: the instruments were confident, well-formed, and had the one number that mattered cropped out. Full write-up as §8 of [../SKINNED-CHARACTER-BUNDLE-FACTS.md](../SKINNED-CHARACTER-BUNDLE-FACTS.md).
