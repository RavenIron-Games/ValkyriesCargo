#### F1 — `Patch_Character_RPC_Damage` makes **every character in the world invulnerable** whenever no merchant is instanced

**Ours:** `ValkyriesCargo/Patches/Patch_Character_Damage.cs:30`

```csharp
if (!__runOriginal || CargoMerchant.LiveCount == 0) return false;
```

**Evidence.** In HarmonyX a bool-returning prefix is folded into `runOriginal` with an `And`, and a
false `runOriginal` branches straight to the return label — the original never runs:

- `scratchpad/hm.cs:190-201` — `if (!AccessTools.IsVoid(method.ReturnType)) { ... Ldloc runOriginal; And; Stloc runOriginal; }`
- `scratchpad/hm.cs:212-213` — `Ldloc runOriginal; Brfalse label;`

`Character.RPC_Damage(long, HitData)` (`asm:8700`, `private void`) is where all damage is applied:
`ApplyDamage` at `asm:8795`, the status-effect/fire/poison adders at `asm:8796-8800`, `Stagger` at
`asm:8718`. `Character.Damage(HitData)` (`asm:8691`) does nothing but `InvokeRPC("RPC_Damage", hit)`.

**Failure.** No visit running (the normal state), `CargoMerchant.LiveCount == 0` on every machine —
permanently 0 on a dedicated server, and 0 on any client not standing next to Ingvar. A player swings
at a Greydwarf: `Character.Damage` → `InvokeRPC` → our prefix returns `false` → `runOriginal = false`
→ `RPC_Damage` never executes → no health change, no stagger, no death. The same holds in reverse: the
player takes nothing. Combat is dead for everyone on the server (the mod is `ModRequired`), except
inside instancing range of a live merchant, where `m == null` correctly returns `true`.

The integrated in-game run did not catch it because a visit was live the whole time and nobody fought.

**Fix.**

```diff
-            if (!__runOriginal || CargoMerchant.LiveCount == 0) return false;
+            if (!__runOriginal) return false;             // somebody ahead of us already cancelled; honour it
+            if (CargoMerchant.LiveCount == 0) return true; // no visit: vanilla, untouched
```

An off-game check cannot catch this. The probe that can: a boot-time assert that
`Harmony.GetPatchInfo(AccessTools.Method(typeof(Character), "RPC_Damage"))` has our prefix, plus an
in-game item "hit a Greydwarf with no visit running and watch it die".

#### F2 — the hover prompt never appears: `Character` is itself a `Hoverable` and wins the lookup

**Ours:** `ValkyriesCargo/Client/CargoMerchant.cs:45` (`: MonoBehaviour, Hoverable, Interactable`),
`:356-364` (`GetHoverName`/`GetHoverText`, the `[E] Trade` / `Shift+E` prompt and the countdown).

**Evidence.**

- `asm:6813` — `public class Character : MonoBehaviour, IDestructible, Hoverable, IWaterInteractable, IMonoUpdater`.
- `asm:10153-10161` — `Character.GetHoverText()` returns `Tameable.GetHoverText()` if a `Tameable` is
  present and **`""` otherwise**. The shipped `Dverger` has no `Tameable` (CLAUDE.md engine facts,
  read live 2026-09-07).
- `asm:39717-39721` — `Hud.UpdateCrosshair`: `hoverObject.GetComponentInParent<Hoverable>()` then
  `GetHoverText()`. `GetComponentInParent<T>` returns the first match **in component order** on the
  GameObject itself before walking parents; `CargoMerchant` is `AddComponent`ed at runtime
  (`Patch_Humanoid_Awake.cs:35`) and is therefore last.
- `asm:19247-19258` — `Player.FindHoverObject` sets `hover` to the collider's own GameObject, and the
  Dverger's `CapsuleCollider` is on the root (`Character.Awake`, `asm:7306`). So the lookup starts at
  the root, where `Humanoid` sits well before us.

**Failure.** A player looks at Ingvar. The crosshair label is `Character.GetHoverText()` = `""`, so
the crosshair stays white and **nothing at all is drawn** — no name, no `[E] Trade`, no `Shift+E`
prompt, no visit countdown. The whole discoverability of the merchant is gone.

`Interact` still reaches us: `Character` does not implement `Interactable` (`asm:112174`) and the
Dverger has no `Tameable`, so `Player.Interact`'s `GetComponentInParent<Interactable>()` (`asm:19270`)
finds `CargoMerchant`. Pressing E works — blind.

**Fix.** A postfix on the two public virtuals, gated on `LiveCount` the way the other two patches are:

```csharp
[HarmonyPatch(typeof(Character), nameof(Character.GetHoverText))]
static void Postfix(Character __instance, ref string __result)
{
    if (CargoMerchant.LiveCount == 0) return;
    var m = __instance.GetComponent<CargoMerchant>();
    if (m != null) __result = m.GetHoverText();
}
```

(and the same for `GetHoverName`). Keep `CargoMerchant : Hoverable` so the text lives in one place.

#### F3 — `VCargo_vanish` and `VCargo_say` are registered and **never invoked**: no Odin vanish, no farewell, and speech on one screen only

**Ours:** `Client/CargoMerchant.cs:110-111` register both handlers. A repo-wide grep for `Keys.Vanish`
/ `Keys.Say` / `InvokeRPC` finds no sender anywhere in `ValkyriesCargo/`.

Consequences, each separately wrong:

1. **The departure is a silent pop.** `VisitDirector.cs:400` → `Spawner.Clear()` → `Spawner.Reclaim`
   → `zdo.SetOwner(session)` + `ZDOMan.DestroyZDO` (`asm:65113`) → the routed `DestroyZDO`
   (`asm:65134`) removes the object on every screen with no effect at all. `CargoMerchant.Vanish()`
   (`:338`), which creates `Odin.m_despawn` (`asm:116195`, `vfx_odin_despawn`, ZNetView-carrying so
   vanilla replicates it once), is dead code. This is the locked decision "Departure — the Odin
   vanish, once per screen", unimplemented.
2. **`Lines.Farewell` never shows**, and `MerchantState.Leaving` (`Spawner.cs` `MerchantState`) is
   never written by anything, so `MerchantPlan`'s terminal state is unreachable.
3. **The arrival line is single-screen.** `Decide` is owner-only (`CargoMerchant.cs:204`) and calls
   `Say(...)` locally at `:293`, not `InvokeRPC(Keys.Say, index)`. `Chat.SetNpcText` (`asm:34745`) is
   pure local UI. A second player standing beside Ingvar sees no bubble — and `_ingvar.Greet()`
   (`:294`) is on the same owner-only path, so the wave animation is single-screen too. The class
   comment at `:14-15` ("the speech has to look the same on every screen") describes a design the code

4. `VisitDirector.cs:190` still carries `// P5: VCargo_say the line` — the one-minute warning is a
   server log line and nothing else.

**Fix.** `End` must ask the merchant to vanish and wait for it (or, minimally, invoke
`Keys.Vanish` before `Spawner.Clear()` and let `Clear` stay as the backstop); `Decide` must
`_nview.InvokeRPC(ZNetView.Everybody, Keys.Say, index)` and let `RPC_Say` do the drawing on every
machine. Note that `RPC_Say` currently resolves through `Lines.Reaction(index)` — the arrival line
needs its own index space or a second handler.

#### F4 — a visit resumed from the sidecar leaves an **immortal permanent merchant** standing in the world

**Ours:** `Server/Spawner.cs` — `Bird`, `Merchant`, `VisitId`, `Dropped` are assigned **only** in
`Author`. `Server/VisitDirector.cs:234-253` (`Adopt`) restores the session but never rebinds them.
`VisitDirector.cs:400` (`End`) calls `Spawner.Clear()`, whose `Reclaim` returns at `Spawner.cs:289`
(`id.IsNone()`).

**Failure.** Server restarts mid-visit. `VisitDirector.Create:112-114` correctly spares the merchant
(`VisitSession.VisitIdOf(_pendingSessionRow)`), the engine restores the event, `Adopt` resumes the
visit — but `Spawner.Active` is `false` and `Spawner.Merchant` is `ZDOID.None` for the whole of it.
When the visit ends, `Spawner.Clear()` reclaims nothing. The merchant's ZDO is `Persistent = true`
(`Spawner.cs:167`), so he stays in the world save with `VCargo_ingvar` set and `VCargo_state = 2`:

- `CargoMerchant.LiveCount` stays ≥ 1 wherever he is instanced, so F1's early-out is bypassed and he
  is genuinely un-killable;
- he is still `Interactable` — `CargoRpc.Open` answers `visit_over` forever;
- the next visit's `Author` (`VisitDirector.cs:376`) creates a **second** merchant beside him.

Only the next boot's `Sweep(keep)` clears him. One orphan accumulates per restart-resumed visit.

**Fix (either).** Rebind on adopt — walk the ZDO table for `VCargo_ingvar == _session.VisitId` and set
`Spawner.Merchant`/`VisitId`/`Dropped = true` — or, cheaper and belt-and-braces, call
`Spawner.Sweep(0)` immediately after `Spawner.Clear()` in `End`; `Sweep` already destroys every
merchant whose visit id is not the live one.

#### F5 — the approach has no distance budget and cannot tell "arrived" from "cannot path", so the merchant declares Trading from wherever he is standing, forever

**Ours:** `Core/MerchantPlan.cs` — `ApproachTimeoutSeconds = 20f`, `TradingLeashDistance = 12f`,
`TradingLeashSeconds = 5f`; `CargoMerchant.cs:270-297`.

**Evidence.**

- `asm:4226-4238` — `BaseAI.Follow(go, dt)`: `StopMoving()` inside 3 m, else `MoveTo(dt, pos, 0f, num > 10f)`.
- `asm:4770-4800` — `MoveTo` calls `StopMoving(); return true;` when `FindPath` fails (`4791`) **or**
  when the path list empties (`4796`). "Arrived" and "no path" are the same return value, and nothing
  in `CargoMerchant` reads it at all.
- `asm:4747-4758` — `FindPath` re-plans at most once a second, and re-uses the cached result for 5 s
  when the target has moved less than 1 m.

**Failure (observed).** The live log in CLAUDE.md's INTEGRATED IN-GAME RUN section:

```
cargo merchant #2: trading (entered: gave up walking after 20 s) [callout]
cargo merchant #2: approaching (entered: the player left: 51.35 m for 5.02 s) [following]
cargo merchant #2: trading (entered: gave up walking after 20 s) [callout]
```

The player was 51 m away. Twenty seconds is a flat constant regardless of the distance at entry, so
from 51 m the timeout **cannot** be met at any Dverger speed once the 1 s repath throttle is included;
and the leash re-enters `Approaching` from *any* distance beyond 12 m, so the pair loops forever. Each
loop the merchant "reaches" Trading standing 51 m from the player, where the terminal's 5 m panel rule
can never be satisfied — the visit is unusable and the log says everything is fine.

The same shape hides a genuine pathing failure: a player on a wooden floor or a roof produces
`FindPath == false` every tick, `MoveTo` returns "arrived", and 20 s later he calls out from the drop
point with no line in the log distinguishing it from a successful walk.

**Fix.** Two changes, both in `MerchantPlan` (pure, so provable):

1. Give `Next` the distance at entry and scale the budget: `timeout = Clamp(distanceAtEntry / 1.5f, 20f, 90f)`.
2. Feed it progress. `CargoMerchant` already measures distance every tick; pass the distance closed
   over the last second. Zero progress for 3 s while outside `approachDistance` is a pathing failure —
   log it as one, and either give up explicitly (`stuck`, a different `Why`) or repath to
   `ZoneSystem.GetGroundHeight` beside the player.

Also raise `TradingLeashDistance` above the distance he can actually cover, or make the leash
re-arm only once.

#### F6 — immortality misses the damage-over-time path; Ingvar can burn to death and take his ZDO and his crossbow with him

**Ours:** `Patches/Patch_Character_Damage.cs` patches `Character.RPC_Damage` only.

**Evidence.** Three status effects call `Character.ApplyDamage` **directly**, never going near
`Damage`/`RPC_Damage`:

- `asm:24777` — `SE_Burning.UpdateStatusEffect` → `m_character.ApplyDamage(hitData, true, false)`
- `asm:25289` — `SE_Poison.UpdateStatusEffect` → same
- `asm:25533` — `SE_Smoke.UpdateStatusEffect` → same

and `ApplyDamage` (`asm:8816`, `public`) reaches `SetHealth(health)` at `asm:8854`. Death is then
`CheckDeath` (`asm:9232`, called from `CustomFixedUpdate` at `asm:7468`) → `OnDeath` (`asm:9244`) →
**`ZNetScene.instance.Destroy(base.gameObject)` at `asm:9314`**, which destroys the ZDO.

The status effect can arrive with no hit at all: `Character.UpdateHeatDamage` adds
`SEMan.s_statusEffectBurning` at `asm:7742` and `asm:7755`, and fire `EffectArea`s do the same.

**Failure.** Ingvar is dropped 12-15 m from the pilot "beside your base" — i.e. among campfires,
hearths and smoke. He walks through one, picks up `Burning` or `Smoke`, and dies mid-visit. The
merchant silently vanishes (no vanish effect — see F3), the visit runs on with nothing to trade with,
`Spawner.Merchant` points at a destroyed ZDO so `Clear` no-ops, and `Humanoid.OnDeath` drops the
Dverger's inventory — the `DvergerArbalest`, `Dverger_melee` and crossbow suit that `UnequipAllItems`
(`asm:14114`) only *unequipped* and never removed — on the ground as loot for the player.

Fall damage is genuinely not a risk and the design's claim is confirmed: `UpdateGroundContact` gates
the fall hit on `IsPlayer()` at `asm:9173`. Drowning is not either: `UpdateWater` (`asm:9785`) only
applies `Wet`/`Tared`.

**Fix.** A second prefix on the public `Character.ApplyDamage`, same shape and same gate:

```csharp
[HarmonyPatch(typeof(Character), nameof(Character.ApplyDamage))]
[HarmonyPriority(Priority.Low)]
static bool Prefix(Character __instance, ref bool __runOriginal)
{
    if (!__runOriginal) return false;
    if (CargoMerchant.LiveCount == 0) return true;
    if (__instance.GetComponent<CargoMerchant>() == null) return true;
    __runOriginal = false; return false;
}
```

#### F7 — `CargoFlight.Floor` inflates the bird's altitude by `m_dropHeight` **every physics step** when the ground raycast fails

**Ours:** `Client/CargoFlight.cs:250-262` (`Floor`), used at `:171` (`ahead.y`), `:183` (`next.y`) and
`:202` (`at.y = Floor(at)` in `Drop`).

```csharp
float ground = p.y;
if (!zs.GetGroundHeight(p, out ground)) ground = p.y;
ground = Mathf.Max(ground, zs.m_waterLevel);
```

**Evidence.** `ZoneSystem.GetGroundHeight(Vector3, out float)`
(`scratchpad/decomp/p4/ZoneSystem.cs:2241-2251`) raycasts down from `y = 6000` against
`m_terrainRayMask` and returns `false` with `height = 0` where no terrain collider exists. Vanilla
raises `y` **only inside** the success branch (`scratchpad/decomp/p4/Valkyrie.cs:126-129` and
`141-145`); ours raises it unconditionally.

**Failure.** On failure `Floor(p)` returns `p.y` (clamped up to the water level), so
`next.y = Mathf.Max(next.y, next.y + 10)` = `next.y + 10`. At 50 Hz that is a **500 m/s climb**. A
zone whose `Heightmap` collider has not finished building — a freshly generated zone at the 90 m
flight start, which is exactly where the bird spawns — puts the bird out of the pilot's active block
within a second; the non-persistent ZDO dies with the instance, the merchant is never dropped, and
`Spawner.Tick`'s orphan branch fires 5 s later with "the bird's ZDO is gone". Nothing in the log says
the bird flew to the moon.

**Fix.** Make "no floor known" mean "leave the altitude alone":

```diff
 private static float Floor(Vector3 p)
 {
-    float ground = p.y;
     ZoneSystem zs = ZoneSystem.instance;
-    if (zs != null)
-    {
-        if (!zs.GetGroundHeight(p, out ground)) ground = p.y;
-        ground = Mathf.Max(ground, zs.m_waterLevel);
-    }
-    return ground;
+    if (zs == null) return float.NegativeInfinity;
+    if (zs.GetGroundHeight(p, out float g)) return Mathf.Max(g, zs.m_waterLevel);
+    return zs.m_waterLevel;              // water is known even where terrain is not
 }
```

`Drop` (`:202`) must keep the authored `y` rather than `-inf` when the floor is unknown — write
`float f = Floor(at); if (f > float.MinValue) at.y = f;`.

#### F8 — both prefab-reading patches assume `ZNetView.Awake` has already run

**Ours:** `Patches/Patch_Valkyrie_Awake.cs:47-50`, `Patches/Patch_Humanoid_Awake.cs:30-33` — both do
`GetComponent<ZNetView>().GetZDO()` and bail when it is null. Component `Awake` order on a GameObject
is the prefab's serialized order, not a guarantee.

**Evidence.** `scratchpad/decomp/p4/ZNetScene.cs:102-104` — `CreateObject` sets the **public static**
`ZNetView.m_initZDO` (declared `scratchpad/decomp/p4/ZNetView.cs:23`) before `Instantiate`;
`ZNetView.Awake` consumes it at `ZNetView.cs:53-56` and nulls it.

**Failure.** If `Valkyrie.Awake` runs before `ZNetView.Awake`, our prefix reads a null ZDO and returns
`true` — vanilla `Valkyrie.Awake` runs (`decomp/p4/Valkyrie.cs:41-70`): `m_instance = this`, then
`Player.m_localPlayer.transform.position` with no null check and a teleport of the local player into
the sky. That is precisely the catastrophe the patch exists to prevent, reached through its own
fallback path. The `Humanoid` twin is quieter: a Dverger with no `CargoMerchant`, a bare vanilla
monster standing in a visit.

**Fix.** Public API, one line each:

```diff
 ZDO zdo = nview != null ? nview.GetZDO() : null;
+if (zdo == null) zdo = ZNetView.m_initZDO;   // our Awake beat ZNetView's; the ZDO is still parked here
```

#### F9 — `LiveCount` is incremented last, after everything in `Awake` that can throw

**Ours:** `Client/CargoMerchant.cs:91` (early return, no increment), `:115` (`LiveCount++` after
`Reassert`), `:133` (`OnDestroy` decrements unconditionally when > 0).

**Failure.** `Awake` throwing is not hypothetical — it is what the catch at `:120-128` was written for,
after a real NRE from `MakeTame`/`SetTamed` on the first live visit. If anything above `:115` throws,
the merchant lives (correctly, by that comment's own argument) but `LiveCount` stays 0, so
`Patch_Character_InIntro` and `Patch_Character_RPC_Damage` both short-circuit: the carry pin's
velocity zeroing and the immortality are off for that whole visit, silently. And a merchant whose
`Awake` bailed still decrements at `:133`, so with two merchants alive (F4's orphan case) it can
subtract another merchant's count.

**Fix.** `LiveCount++` as the first statement of `Awake`, plus a `bool _counted` so `OnDestroy`
decrements only what it added.

#### F10 — `Reassert` owner-gates fields that are local-only, so a non-owner machine keeps the Dverger's faction, and `m_tamed` diverges

**Ours:** `Client/CargoMerchant.cs:152` gates the whole method on `_nview.IsOwner()`.

**Evidence.** `m_faction` (`asm:6887`, `public Faction m_faction`), `MonsterAI.m_alertRange`
(`asm:5640`), `BaseAI.m_aggravatable` / `m_passiveAggresive` (`asm:3917`/`3919`) and
`m_randomMoveRange` (`asm:3881`) are plain local fields with no replication path. `m_tamed` does
replicate — but only through the ZDO read in `Character.Awake` (`asm:7339`): `RPC_SetTamed`
(`asm:10607`) assigns `m_tamed` **only on the owner** (`if (m_nview.IsOwner() && m_tamed != tamed)`),
so a client that already had the merchant instanced when the tame fired keeps `m_tamed == false` for
the life of that instance.

**Failure.** On a second client, Ingvar is a `Dvergr`-faction, untamed Dverger for AI purposes. Today
the practical effect is small — `BaseAI.IsEnemy` (`asm:4994-5085`) returns the same answer for
`Dvergr` vs `Players` as it does for tamed vs `Players` — but any AI that machine owns evaluates a
different creature from the one the owner sees, and `EnemyHud` colours him as a hostile.

**Fix.** Split `Reassert` in two: a local half (`m_name`, `m_faction`, the four AI fields, `NpcTalk`)
that runs on every machine, and a networked half (`SetTamed`, `MakeTame`, `UnequipAllItems`) that stays
owner-only.

#### F11 — vanilla monsters treat a tamed Ingvar as an enemy, and he can neither die nor fight back

> **DECIDED 2026-09-07 (owner): ghost mode**, and built on Track A's side the same day: a `Priority.Low`
> prefix on the static `BaseAI.IsEnemy(a, b)` answers "not enemies" for any pair with the merchant in it
> while a visit runs (`Patches/Patch_BaseAI_IsEnemy.cs`; the decision pure in `Core/Ghost.cs`, checked).
> Neither of the two shapes below; the tame stays, and nothing targets or fears him.

**Evidence.** `BaseAI.IsEnemy(a, b)` at `asm:5011-5021`: with `b.IsTamed()` true and the attacker's
faction neither `Players` nor `Dverger`, the method falls through to `return true`. A tamed creature is
a legitimate target for every hostile in the game — that is how tamed wolves work.

**Failure.** A Greydwarf pack or a raid targets Ingvar. He is immortal (once F1 is fixed), has no
weapon (`UnequipAllItems`), and — because our `RPC_Damage` prefix cancels the whole method — is never
even staggered or pushed back (`Stagger` at `asm:8718`, `ApplyPushback` at `asm:8754` are both inside
it). The result is an unkillable, unmovable aggro magnet parked next to the player's base for 300 s.

**Fix or decision.** Either leave `m_faction = Character.Faction.Dverger` and rely on faction alone
(`asm:5068-5073`: `Dverger` is not an enemy of `Players`, `AnimalsVeg` or `Boss`), dropping the tame —
but the tame is what `AvoidFire` (`asm:4387`) and the tamed target-clearing (`asm:5886-5899`) rest on —
or accept it and document that Ingvar draws aggro. Worth an explicit decision, not a default.

### NOTE

- **N1** `FlightPlan.Make`'s descent-slide `while` loop is unreachable. `PointInBlockWithMargin` is the
  intersection of two axis-aligned boxes, hence convex; with `activeArea ≥ 2` the pilot always
  satisfies it (`|p − zoneCentre| ≤ 32 ≤ half − 8 = 88`) and the loop above has proved the start does,
  so every point on the segment — the drop and the descent waypoint included — is inside. Untested code
  that reads as load-bearing.
- **N2** `Make` never tests the DROP point against the block at all (only the start and the descent).
  N1's convexity saves it for `activeArea ≥ 2`; at `activeArea == 1` the margin box is
  `half − EdgeMargin = 32 − 8 = 24 m`, so a pilot standing more than 24 m from their own zone centre
  fails it and the argument collapses. One explicit check, or a comment saying why not.
- **N3** `MerchantPlan.ShouldPin(state, carrierResolved)` is only ever called with `true`
  (`CargoMerchant.cs:243`); the second parameter exists for the harness.
- **N4** `RPC_Say` (`CargoMerchant.cs:302`) and `RPC_Vanish` (`:309`) have no try/catch; a throw in a
  `ZNetView` handler unwinds into `ZRoutedRpc`'s dispatch loop. Dead today (F3) — fix them when wired.
- **N5** `ZNetView.Register` is `m_functions.Add(hash, ...)` (`decomp/p4/ZNetView.cs:280`) — a
  **Dictionary.Add**, which *throws* on a duplicate name, unlike `ZRpc.Register` which replaces. Safe
  today because `Patch_Humanoid_Awake.cs:34` guards the `AddComponent`, but it is the reason a second
  add must never happen.
- **N6** `BaseAI.SetPatrolPoint()` (`asm:4077-4083`) writes `ZDOVars.s_patrol` and `s_patrolPoint` on
  the merchant's **persistent** ZDO, and `CargoMerchant` never calls `ResetPatrolPoint()`
  (`asm:4085`). Two vanilla keys of ours-by-proxy end up in the world save, and after the first
  Trading his idle centre is pinned wherever he timed out.
- **N7** `CargoTick.EndSession` does not reset `Spawner`'s statics, so `cargo status` reports a stale
  flight after leaving a world. Not dangerous — `ZDOMan.m_sessionID` is regenerated per world
  (`asm:64540`, `asm:64867`), so a stale `ZDOID` cannot resolve in a new session — but it lies.
- **N8** `Spawner.Sweep` looks up merchants by the **current** `Server.BodyPrefab`. Change that config
  between sessions and every merchant authored under the old prefab is unreachable by the sweep:
  a permanent, immortal, interactable NPC that nothing will ever clean up.
- **N9** `Decide` follows `Player.GetClosestPlayer` (`asm:20318`), not the pilot. With two players he
  re-targets every tick.
- **N10** CLAUDE.md:126-128 and `BodyLoader.cs` say `NpcTalk.Start` "WILL run" after a P5 attach. It

  behaviour, so the `GetComponentInChildren<Animator>()` at `asm:6625` never happens. The doc is
  pessimistic in the safe direction, but it is wrong.
- **N11** `CargoMerchant` is a third, undocumented exception to house rule 2 (it owns `FixedUpdate`
  and `LateUpdate`). The rule's written exception list names only `IngvarBody` and `CargoFlight`.
- **N12** `Character.SetVisible` (`asm:10583`) only moves `m_lodGroup.localReferencePoint`; it never
  touches `Renderer.enabled`. `BodyLoader.cs:576-579` has this right; CLAUDE.md:121-122's "would
  switch them back on" overstates it — `VisEquipment.UpdateLodgroup` is the one that refills the LOD
  renderer list.
- **N13** `UnequipAllItems` (`asm:14114`) unequips but does not remove. The arbalest, the melee weapon
  and the suit stay in his inventory; `MonsterAI.Start` re-equips on the owner (`asm:5786-5793`) and
  `SelectBestAttack` re-equips whenever a target exists (`asm:6321-6326`). Between instantiation and
  the 0.5 s re-assert he visibly holds a crossbow, and F6's death drops the lot as loot. An
  `m_inventory.RemoveAll()` after the first successful assert would end it.
- **N14** `CargoFlight.Fly` writes `s_velHash` every FixedUpdate, marking the bird's ZDO dirty at
  50 Hz for the whole flight. It is correct — `ZSyncTransform`'s non-owner path extrapolates from that
  key (`decomp/p4/ZSyncTransform.cs:353-359`, capped at 2 s) and `OwnerSync` will not overwrite it
  because `GetVelocity()` never changes from its cache (ibid. `176-182`) — but it is 17 s of one ZDO
  in every send list, and a per-metre threshold would cost nothing.
- **N15** `Patch_Character_InIntro` changes behaviour from a postfix at default priority, where house
  rule 1 asks for prefixes at `Priority.Low` for behaviour. Defensible (it decorates a result), but it
  is a deviation and is not written down.

## 3. What was checked and found correct

**Authoring and the ZDO contract.** `CreateNewZDO` genuinely does not set the prefab (`asm:64865-64886`
— the hash is used only for the portal list), so `Spawner`'s explicit `SetPrefab` is required and
present. `ZNetView.Awake`'s init-ZDO branch re-applies `Type` and `Distant` for an owner but never
`Persistent` (`decomp/p4/ZNetView.cs:53-64`), so the bird's non-persistence and the merchant's
persistence survive as authored — `Spawner`'s comment is exactly right. `ZDO.Set` has no ownership
check on any overload and `okForNotOwner` is ignored (`asm:62236-62242`); the house rule is an API
fact. `ZDOMan.DestroyZDO` is a no-op for a non-owner (`asm:65113-65118`), so `Reclaim`'s
SetOwner-then-destroy is the only shape that works, and the destroy reaches every machine through the
routed `DestroyZDO` (`asm:65134`, `asm:65147`).

**Ownership through the visit.** `ReleaseNearbyZDOS` skips non-persistent ZDOs outright
(`asm:65094`), so the pilot keeps the bird for the whole flight and no second client can steal it.
For the persistent merchant it does the handover the design needs: the server's own pass finds nothing
(its reference position is pinned a million out), and each peer's pass claims any ZDO whose owner is
not inside its own active area (`asm:65099-65109`) within the 2 s `ReleaseZDOS` timer
(`asm:65057-65069`, server-only via `asm:65000`). That is what makes the boot sweep's
`SetOwner(server)` recoverable: a client walking up takes the merchant over and `Reassert`/`Decide`
resume from `VCargo_state`. A pilot who disconnects mid-flight loses the bird to
`RemoveOrphanNonPersistentZDOS` (`asm:65573-65585`), which is exactly what `Spawner.Tick`'s 5 s orphan
grace is written for.

**Zone maths.** `ZNetScene.InActiveArea(zone, centre, activatedArea)` is `|Δ| ≤ activatedArea` on both
axes (`decomp/p4/ZNetScene.cs:384-391`) and `ReleaseNearbyZDOS` passes `m_activeArea − 1`
(`asm:65091`). `FlightPlan.InActiveArea`'s `reach = activeArea − 1` matches exactly, and
`ZoneSystem.m_activeArea` is read at runtime rather than assumed (`Spawner.Author`).

**The carry.** `Character.InIntro()` is `public virtual bool` returning false (`asm:9738`); `Player`
overrides it (`asm:20952`) so the postfix cannot touch a player. Its one relevant caller is
`Character.UpdateMotion` (`asm:7940-7961`), reached only on the owner through `CustomFixedUpdate`
(`asm:7449-7456`) — the design's description of what it does (zero the Rigidbody, pin
`m_maxAirAltitude`) and what it does not do (grant immunity) is exact. Fall damage is `IsPlayer()`-gated
(`asm:9173`), so a carried or dropped Dverger takes none, and the `PinToTalon` two-write pattern
(FixedUpdate + LateUpdate) matches vanilla's own `SyncPlayer`/`LateUpdate` shape
(`decomp/p4/Valkyrie.cs:85-97`).

**The Awake-ordering class of bug (the PR #22 lesson), swept.** `Humanoid.Awake` (`asm:12932`) calls
`base.Awake()` first, so by the time our postfix runs `Character.Awake` (`asm:7303-7367`) has cached
`m_collider`, `m_body`, `m_zanim`, `m_nview`, `m_animator`, `m_animEvent`, `m_visual`, `m_lodGroup`,
built the `SEMan` and registered `RPC_Damage` — everything `CargoMerchant.Awake` touches on the
Character side exists. `Humanoid.Awake` does **not** hand out default items; `Humanoid.Start` does
(`asm:12947-12953`), so the corrected comment in `Patch_Humanoid_Awake` is right and the older one was
wrong. `MonsterAI.MakeTame` opens with `m_character.SetTamed` (`asm:5837`) and `BaseAI.m_character` is
assigned in `BaseAI.Awake` (`asm:4016`) — the `fromAwake` fix is the correct one, and `BaseAI.Awake`
resets none of the fields `Reassert` writes (`asm:4012-4053`). `MonsterAI.Awake` (`asm:5758-5782`) is
likewise safe to precede. `NpcTalk` has **no** `Awake` at all — its setup and its `InvokeRepeating` are
in `Start` (`asm:6621-6630`) — so disabling the component in our `Awake` is enough and nothing leaks
(this is stricter than the docs claim; see N10). The one remaining ordering assumption is `ZNetView`'s,
which is F8.

**The follow branch is genuinely reachable.** With no weapon, `SelectBestAttack` returns
`GetCurrentWeapon()` = null without re-equipping (`asm:6316-6328`, the re-equip is gated on having a
target), so `MonsterAI.UpdateAI` falls into `if ((m_targetStatic == null && m_targetCreature == null) ||
itemData == null) { Follow(m_follow, dt); }` (`asm:6075-6087`). `m_alertRange = 0` is a real defence
and not a guess: `UpdateTarget` clears `m_targetCreature` whenever it is further than `m_alertRange`
from the follow target or the patrol point for a tamed character (`asm:5886-5899`), and `AvoidFire`
returns false outright for a tamed character (`asm:4387-4390`). `m_aggravatable = false` keeps him out
of `AggravateAllInArea` (`asm:8731-8734`). He does not attack players: `IsEnemy` returns false for a
tamed creature against `Faction.Players` (`asm:5017`).

**Interaction.** `Character` is not `Interactable` (`asm:6813` vs `asm:112174`) and the Dverger has no
`Tameable`, so `CargoMerchant` is the only `Interactable` on the object and `Player.Interact`'s
`GetComponentInParent<Interactable>()` (`asm:19270`) finds us. Only the `Hoverable` half is broken (F2).

**The sweep's timing.** `ZNet.Start` → `ServerLoadWorld` → `LoadWorld` → `m_zdoMan.Load`
(`asm:66923-66940`, `asm:68310`) is synchronous inside `Start`, so the first `CargoTick.Update` that
builds the director (`CargoTick.cs:122`) already sees a fully loaded ZDO table. The `keep` id is right:
`VisitSession.VisitIdOf(_pendingSessionRow)` (`VisitDirector.cs:112-113`) spares a merchant waiting to
be adopted, and `SweepAfterGivingUp` (`:269-273`) closes the other half when adoption fails. Clearing
`VCargo_carrier` on the kept merchant is correct and necessary — `ZDO.Load` renumbers every id, so the
saved `ZDOID` is a live handle to an unrelated object.

**The pilot-writable drop point.** `Spawner.Tick` reads `VCargo_target` off a ZDO the client owns and
bounds it with `FlightPlan.DropAccepted`, written `!(d <= tol)` so a NaN refuses; `AuthoredDrop` is not
persisted and is the fallback. That is the only path from a client write into server state in P4/P5 and
it is closed.

private (`asm:8700`), `Character.Damage(HitData)` public (`asm:8691`), `Character.ApplyDamage(...)`
public (`asm:8816`), `Character.InIntro()` public virtual (`asm:9738`), `Character.SetTamed(bool)`
public (`asm:10599`), `Character.m_faction` public (`asm:6887`), `Character.m_name` public
(`asm:6883`), `Character.IsOnGround()` public (`asm:9223`), `Humanoid.UnequipAllItems()` public
(`asm:14114`), `MonsterAI.MakeTame()` public (`asm:5837`), `MonsterAI.SetFollowTarget(GameObject)`
public (`asm:6543`), `MonsterAI.m_alertRange` public (`asm:5640`), `BaseAI.SetPatrolPoint()` public
(`asm:4072`), `BaseAI.IsEnemy(Character, Character)` public static (`asm:4994`),
`Player.GetClosestPlayer(Vector3, float)` public static (`asm:20318`), `Chat.SetNpcText(...)` public
(`asm:34745`), `EffectList.Create(Vector3, Quaternion, Transform, float, int)` public (`asm:29968`),
